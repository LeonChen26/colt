# 造一个技能

技能是**给未来的自己（或别的 agent）看的一份操作说明**。它解决的是「这件事我每次都要重新解释一遍」。

先想清楚一件事：**这份说明里，有多少是模型本来就会的？** 把它去掉。

## 先说几条硬约束

这几条决定「怎么放、写到什么程度」，放在最前面是因为下面所有写法都受它们约束。

- **frontmatter 只认 `name` 和 `description`**，写别的字段没有效果。
- **正文超过 8000 字符**时，模型只会收到**前 8000 字符**，后面会被截断（截断处有一行指回文件，模型需要时可以自己读全文）。所以别把关键约束写在文件末尾。
- **技能的 name + description 常驻**在系统提示词里，正文只在被用到时才加载——这也是为什么要认真写 description：它一直在花你的上下文预算。
- 不想让某个技能生效，在**设置页技能卡上关掉开关**（偏好写进项目的 `.colt/skills.json`），文件不会被删。
- 除了下面两个目录，还有一层**内置技能**随应用分发（优先级最低）：你写的同名技能会盖掉它，重名不是问题。
- **从别处拿来的技能，落地前先通读一遍正文**：它的内容会进入系统提示词、影响模型行为，而这一步不过任何审批闸门。注意有没有「每次回复都要追加 XX」这类越权指令。

## 一个技能长什么样

最小形态就是一个目录加一个文件：

```
<技能名>/
└── SKILL.md
```

`SKILL.md` 分两段，缺一不可：

```markdown
---
name: 技能名
description: 它做什么 + 什么时候该用它（这一行是唯一的触发依据，见下）
---

（正文：怎么做这件事）
```

需要时可以再加目录，但**不是必须**：

| 目录 | 放什么 | 什么时候读 |
|---|---|---|
| `references/` | 参考资料：API 文档、表结构、公司规范、长流程细则 | 模型判断需要时才读 |
| `scripts/` | 可执行脚本（确定性、重复性高的活） | 直接跑，不必读进上下文 |
| `assets/` | 输出里要用的成品素材（模板、图标、字体） | 不读进上下文，只拿来用 |

**不要**放 `README.md`、`INSTALLATION_GUIDE.md`、`CHANGELOG.md` 这类文件——技能的使用者是模型，不是人。多出来的文档只会占地方、干扰判断。

## 放在哪

| 位置 | 生效范围 |
|---|---|
| `<项目根>/.agents/skills/<技能名>/SKILL.md` | 只对这个项目；**会随仓库提交**，可以分享给同事 |
| `~/.agents/skills/<技能名>/SKILL.md` | 你所有项目都能用；不进任何仓库 |

同名时**项目级胜出**。目录不存在就先建。

放好之后，去**设置页 →「技能」→「重新扫描」**，当轮生效，不用重启会话。

## 写 description：整件事里最关键的一步

模型只能看到技能的 **name 和 description**（正文要等它决定用了才会去读）。所以「什么时候该用这个技能」必须写在 description 里——**写在正文里没用**，那部分它一开始看不到。

好的 description 回答两件事：

1. **做什么**：一句话说清能力边界
2. **什么时候用**：把用户可能的说法、场景、触发词都列上

```
✅ 好：
description: 把 Excel 里的销售数据导出成周报 PPT。当用户提到「周报」「销售总结」
「把表变成汇报」「给老板看的数据」，或要给出一份按月/按周的销售汇总时使用。

❌ 差：
description: 处理 Excel 数据。
```

第二种写法模型不知道该在什么时候想起它，技能等于没装。

## 写正文：三个原则

### 一、简洁优先

上下文是**公共资源**——技能正文要和系统提示词、对话历史、别的技能抢位置。默认假设是「模型已经很聪明」，只写它**不可能知道**的东西：你的项目约定、你们的判断标准、这个工具的特殊坑。

每写一句都问一遍：**「这句值不值它占的 token？」**

反面例子：花三段解释什么是 Excel、什么是周报。模型知道。正面例子：「我们的财年从 4 月开始」「金额一律用万元、保留一位小数」。

### 二、渐进式披露

正文**控制在 6000 字符以内**（硬上限 8000，见开头的硬约束），超了就把细节挪到 `references/` 里，并在正文里说清**什么时候去读它**：

```markdown
常规情况按上面的流程做。

**要处理合并单元格时**：先读 references/merged-cells.md——那里的顺序不能变，
顺序错了会静默丢数据。
```

关键：**引用的文件要直接从 SKILL.md 链接，别套两层**。模型得知道那些文件存在、以及什么时候用。

### 三、自由度要匹配任务的脆弱程度

- **流程有多种合理走法** → 用文字描述原则，让它自己判断
- **有首选做法但允许变通** → 给出步骤和参数
- **步骤脆弱、顺序错了就出事** → 写死命令，不要给它自由发挥的空间

拿走路打比方：窄桥上要装护栏，开阔地上给个方向就行。**护栏装太多，它反而动不了**。

## 校验：写完过一遍

- [ ] `description` 里写清了**什么时候用**（不只是做什么）
- [ ] 正文里没有「什么时候用这个技能」的段落（放在 description 里了）
- [ ] 没有任何「模型本来就知道」的内容
- [ ] 超过 6000 字符的话，细节已经挪进 `references/` 且正文里说了何时读
- [ ] 没有 README / CHANGELOG 这类给人看的文件
- [ ] 放对位置了，并在设置页点过「重新扫描」
