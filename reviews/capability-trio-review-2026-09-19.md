## 0. 一句话结论

**这三个功能在做同一件事**——把磁盘上的外部声明变成「模型看得见、模型调得动、用户管得住」的能力——
**却写出了三套完成度差一档的实现**。技能最好（有管理面、有热更新、有禁用、有来源），MCP 次之（有管理面、
有热更新、无禁用），子代理最薄（**没有管理面、没有热更新、没有禁用**，装了什么全靠一条 5 秒 toast）。

由此产生两类问题：**稳定性**上，MCP 的连接被放在会话启动的串行关键路径上，可以在不开任何报错的情况下
把会话拖到「启动超时」；**易用性**上，三个功能的「改完怎么生效」分别是「点重新扫描」「点重新加载」
「重启会话（且没地方告诉你）」。

## 2. 稳定性问题

### S1 · P0 · MCP 连接在会话启动的**串行关键路径**上，能把会话拖成「启动超时」，且报错指错地方

**证据链**：

1. `entry.ts:383`：`const mcp = await createMcpRuntime(...)` —— 在 `AgentHarness.create`（`:389`）**之前**；
2. `mcp-tools.ts:581-599`：`doReload` 对每台 server **串行** `await connectServer`；
3. `mcp-tools.ts:429-430`：每台最坏 `MCP_STEP_TIMEOUT_MS`（连接）+ 同值（列工具）；
4. `limits.ts:40`：`MCP_STEP_TIMEOUT_MS = 15_000` ⇒ **每台最坏 30s**；
5. `session-manager.ts:59`：`READY_TIMEOUT_MS = 120_000`，超时则
   `:790` `reject(new Error("会话进程启动超时（120s），请重试。"))`。

**合起来的后果**：**4 台**连不上 / 起得慢的 server（用户级配置是全局生效的，配 2 台 + 项目级 2 台很常见）
就把 init 拖到 120s，**会话直接打不开**；而用户看到的报错是「**会话进程启动超时，请重试**」——
重试一次还是 120s，因为真实原因是某台 server 连不上，而那条诊断（决策 5 精心写的）此刻还没机会发出来。

这不是「理论上可能」：`mcp-slow-fixture-server.mjs` 已经证明「一个不说话的 server 能把连接耗到 15s」，
决策 15 也承认了「多台 server 同时需要重连会**叠加**」——**同样的叠加在启动路径上一次都没被测过**
（`mcp-reload` 冒烟测的是**会话已就绪之后**的重载，不是冷启动）。

**修法**（按性价比排序，三者可分期）：

- **① 并行**（半天）：`doReload` 的连接循环改 `Promise.all`。4 台并行 ⇒ 最坏 30s。改动小、收益确定。
- **② 启动预算 + 后台补齐**（推荐，一天）：init 不等连接——先建 harness（此时工具数组不含 MCP），
  并行发起连接，连完走**现成的** `reloadMcpIntoHarness`（`mcp-reload.ts:29`，`setTools` + `healLaneTools`）。
  给一个**启动预算**（如 8s）：预算内连完的照常进首批工具，超时的转后台、连上再补，并发一条诊断。
  ⚠️ 走这条路要补一条断言：**「预算内没连完时会话必须照常可用」**——否则会变成另一种「点了没反应」。
- **③ 错误归因**（若只做 ① 则必做）：init 超时时把「卡在哪台 server」带进那条 reject 文案，
  别让用户对着「请重试」重试。

**判据**：扩展 `COLT_SMOKE_MODE=mcp-reload`（免费、不调模型）——夹具放 3 台「一句话不说」的 stdio server，
断言「会话在 X 秒内就绪且可用」；把 `Promise.all` 改回 `for await` 该条立刻红。

### S2 · P0 · 热重载只 heal **主 lane**，拿过 MCP 工具的子代理 lane 会在删 server 后当场炸

**证据链**：

1. `mcp-reload.ts:29-46`：`reloadMcpIntoHarness(mcp, harness, lane, context)` 只 heal **传进来的那一个 lane**；
2. `entry.ts:997` 传的是 `state`（当前 worker 的 `lane` = 主 lane）；
3. `subagent.ts:521-522`：`def.tools === null` 时白名单 = `harness.getTools()` 全集（只剔除 `subagent` 自身）
   ⇒ **`general` 兜底定义（`agent-defs.ts:140-142`，`tools: null`）会拿到当时全部 MCP 工具**；
4. `subagent.ts:539`：`lane.setActiveTools(allowed)` 之后，**子代理 lane 的清单再没人更新过**
   （`#spawn` 之外全仓没有第二处对子 lane 调 `setActiveTools`）。

**后果**：用户在设置页点「重新加载」并**删掉**一台 server（或它掉线后被移除）→ 主 lane 被 heal 干净了，
而**在跑的 `general` 子代理的清单里仍留着 `mcp__x__y`** → 它下一次生成时工具定义已不在 `toolsByName` 里 →
`configured_tools_unavailable`。而这段注释（`mcp-reload.ts:20`）自己写着「**删掉的工具尤其要连清单一起删**」——
现在只删了主 lane 那份。

**修法**：`reloadMcpIntoHarness` 里遍历 `harness.lanes()`，**按每个 lane 自己的白名单与新的 harness 工具集求交**
（不是把主 lane 的清单复制过去——那会破坏子代理的硬白名单，把 `researcher` 变成全能）。
`Subagents` 需要暴露「在跑的子 lane 名单 + 各自允许集」（它本来就持有 `#runs`），或统一走
`lane.getActiveTools()` ∩ `harness.getTools()`。

**判据**：单测（免模型）——建一个 `tools: null` 的子代理并让它持有一个 MCP 工具名，再 reload 删掉该 server，
断言子 lane 的 `getActiveTools()` 里那个名字**已消失**且 harness 工具集自洽。

### S3 · P1 · 子代理的墙钟把「等用户审批」的时间也算进去

`subagent.ts:68`：`MAX_SUBAGENT_MS = 10 * 60 * 1000` 是**墙钟**。而子代理内部的写 / 执行工具会走
`before_tool` 弹卡，最长等 `APPROVAL_TIMEOUT_MS = 5min`（`limits.ts:26`）；一个需要 **3 次审批**的子代理，
光等用户就能耗掉 15 分钟——**墙钟早已到点把它中止了**，而用户只是在外面吃了个饭。

更糟的是这时的中止文案是「超过时间上限」，用户会以为是任务复杂，而不是「你在弹卡上没点」。

**修法**：`before_tool` 挂起期间**暂停**子代理墙钟（记录挂起起点，放行时补偿）；或在超时判定前扣除
「等待人工」的累计时长。补偿要设上限（不能因为用户挂一夜而无限延长）。

**判据**：需要一个可调的测试缝（如 `COLT_SUBAGENT_MAX_MS`），冒烟里造「子代理内弹卡 → 等 30s → 批准 →
墙钟设 20s → 断言它**没有**被中止」。没有这个缝这条就只能靠代码审查（如实记下）。

### S4 · P1 · 子代理定义**没有热更新**，且没任何地方告诉用户

`entry.ts:321` `loadAgentDefs(...)` 只在 create-time 跑一次，`entry.ts:378` 把 `agents.agents` 以**静态数组**
交给 `Subagents`；`renderAgentCatalog` 每请求重拼，但拼的是那份**不变的** `defs`。

对照：技能有「重新扫描」当轮生效（A2 已修），MCP 有「重新加载」当轮生效。**子代理只能重启会话**——
而「写一个 agent 定义」是分钟级动作，恰恰是最需要「刚写完就想试」的那一类内容。这条与技能报告 A2 是
**同一个病，且更重**（技能至少还有个 rescan 按钮）。

**最小修法**（半天，无需新 UI）：把 `SubagentDeps.defs` 从 `readonly AgentDef[]` 改成
`() => readonly AgentDef[]`（取值器），加一条与 `skillsRescan` 同构的命令重载定义；目录块本来就每请求重拼，
改完自动生效。**设置页面留到 S6 一起做**。

⚠️ 边界：`#spawn` 已经建好的 lane 不受影响（正在跑的用旧定义是对的），只影响之后的委派——要在文案里说清。

### S5 · P1 · reload / rescan 只作用于**当前会话的 worker**，同项目的其它会话仍用旧配置

`session-manager.ts:1341-1350`：`mcpStatus(sessionId)` / `mcpReload(sessionId)` 都是「按 sessionId 找那一个 worker」。
而 worker 是**每会话一个**（池上限 6）。

**后果**：用户开着 3 个同项目会话，在设置页点「重新加载」→ 只有当前那个拿到新工具清单；另外两个会话的
模型**仍然看得到已被删除的 MCP 工具、看不到新装的**。设置页的措辞是「改完点『重新加载』即可生效」——
对其它两个会话是假的。

**修法**：`#queryMcp` 改成「对该项目下**所有活 worker** 广播」（主进程本来就持有 worker 池）；
`SKILLS_QUERY_TIMEOUT_MS` 那条同构路径一起改。技能与 MCP 两条都要改，只改一条会变成新的不对称。

### S6 · P1 · 子代理是三功能里唯一**没有管理面**的，且它的启动播报是「状态当事件」

- `Settings.tsx` 里 `子代理` / `subagent` **零命中**（技能与 MCP 都有分区）。
- `agent-defs.ts:280-300` `describeAgents` 每次 worker 启动都发「**已加载 N 个子代理定义**（项目级 X · 用户级 Y）」——
  这正是技能报告 P4 指出、且**已经在技能侧修掉**的「状态当事件播报」（技能现在只报事件：遮蔽 / 解析失败 /
  不对模型公开）。子代理这条还在，于是每次 worker 重启都往「事件」页签灌一条例行信息。
- 同一函数里 `loaded.shadowed.join("、")` 是**纯名字数组**，不区分「跨来源遮蔽」与「同目录重名」——
  这正是技能报告 A6 修掉的那条：**会把同目录重名说成「项目级覆盖了同名用户级」**，一句假话。
  而这里（`agent-defs.ts:289`）恰好是用户唯一能看到「谁被遮蔽了」的地方。

**修法**：照抄技能侧已验证的三件套——① `describeAgents` 收窄成只报事件；② `shadowed` 带 `from`/`by`
（复用 `ShadowedSkill` 的语义，或抽到 shared）；③ 设置页新增「子代理」分区（列表 / 定义正文 / 来源 /
遮蔽告警 / 重新扫描），与技能分区同构。

### S7 · P2 · 「能力注入」三件套的共同债：create-time 装载 × 每请求注入，三者解法不一致

| 注入物 | 注入时机 | 解法 |
|---|---|---|
| AGENTS.md / 记忆 / todo / MCP instructions | 每请求重读 | 内容每请求重拼 |
| 技能清单 | 每请求重拼 + 容器可换 | `setResources` 热更新（已做对） |
| MCP 工具 | 真注册进内核 | `setTools` + `healLaneTools`（已做对，**但只 heal 主 lane**，见 S2） |
| **子代理定义** | 每请求重拼目录块，**清单不可换** | **未做**（S4） |

统一判据（建议写进 `ARCHITECTURE.md`）：**装载一次、注入每请求、热更新只换容器**。凡是「每请求重拼的东西
来自一份 create-time 快照」的组合，都是潜在的静默不一致——现在只剩子代理这一处。

### S8 · P2 · 其它稳定性条目（各一行，不展开）

- **MCP 工具数量无上限**：一个 server 暴露 80 个工具、配 3 台 ⇒ 200+ 工具全进系统提示词与审批面。
  建议加「单会话 MCP 工具总数上限 + 超出告警」（与 `MAX_CONCURRENT_SUBAGENTS` 同款取舍，是**上下文与注意力**闸）。
- **多会话重复起 stdio 子进程**：worker 每会话一个 ⇒ 同一个 server 开 5 个会话起 5 份进程；
  worker 空闲回收又会把**有状态 server** 的会话状态带走（browser / DB 类），用户无从知晓「为什么之前的上下文没了」。
  短期：设置页说明「每个会话独立连接」；长期：考虑连接下沉到主进程或独立守护进程（大改，先出方案）。
- **子代理无会话级预算闸**：并发 3 只是**瞬时**闸，不是总量闸；模型在一轮里串行委派 20 次（每次几分钟）
  没有任何上限，界面上只有一张张卡片。建议：会话级「累计子代理运行时间 / 费用」上限 + 界面显示累计数。
- **视图推送压力**（与全局 F7 同源）：`subagent.ts:342` 对**运行中**的子代理每次 `toView()` 都全量投影，
  而 `toView()` 随视图每 50ms 重推 ⇒ 3 个并行子代理 = 每 50ms 投影 3 份完整 transcript。
  建议：运行中的也加「内容哈希不变则复用上一次的投影对象」（已有 `#frozenViews` 的引用稳定思路，扩大到 running 分支）。

## 3. 易用性问题

### E1 · 三套心智：「改完怎么生效」和「怎么关掉」各说各话

| 想做的事 | 技能 | MCP | 子代理 |
|---|---|---|---|
| 改完生效 | 设置页「重新扫描」 | 设置页「重新加载」 | **重开会话**（且没人告诉你） |
| 关掉一个 | 设置页开关 | 注释掉配置文件 | **没地方关** |
| 看装了什么 | 设置页列表 | 设置页列表 | 一条 5 秒 toast |
| 看来自哪一层 | 列表里写着 | **看不出来** | toast 里的合计 |

用户不需要记住三个功能是三个团队做的。**建议**：先做**契约对齐**（`McpServerView` 加 `source`；
三者都支持 `disabled`），再做**界面同构**（设置页三个分区共用一套「列表 + 开关 + 告警 + 刷新」骨架）。
成本主要在契约，不在界面。

### E2 · MCP 的 `${VAR}` 与 `secrets` 完全脱节：agent 装完往往连不上

决策 21 把安装方式定为「让 agent 自己写配置」，并立了规矩「密钥一律 `${VAR}`、不写明文」。
但 `${VAR}` 的取值来源是 `process.env`（`mcp-tools.ts:585`），而 Colt 自己的凭据库是 `main/secrets.ts`
（safeStorage）。**用户没有地方设置这个 VAR**（得改系统环境变量并重启应用），于是最常见的结局是：
agent 高高兴兴写完配置 → 重新加载 → 一条「server X 缺少环境变量 TOKEN」→ 用户卡死。

**建议**：设置页 MCP 分区补一个「环境变量」输入（存 `secrets`，注入 worker 的 env），
或支持 `.colt/mcp.env`（明确不进 git）。**这条不做，「让 agent 自己装」这个产品决定就是半截的。**

### E3 · MCP 掉线后工具仍留在清单里：模型会反复去调一个必然失败的工具

决策 11 的选择（留着、调用如实失败）在**诚实性**上是对的，但在**易用性**上有代价：模型不知道它掉线了，
只会看到「调用失败」，于是重试、换参数再试，每一轮都烧钱。而用户唯一的线索是设置页某个红点（得自己点开）。

**建议**：保留「不伪造成功结果」，但**让错误文案指路**——`callTool` 抛错时若该 server 已 `error`，
把「server X 已掉线，请在设置页点重新加载」拼进错误消息里（模型看得见，就知道该停而不是该重试）。
成本极低（一处字符串），收益是止住一轮无意义的重试。

### E4 · 子代理的失败可恢复性：一次委派失败，模型会重试、再失败

`buildResultText` 已经很诚实地给出了「别把它当成做完了」。但**没有重试上限**：同一个 `task`
失败三次，模型大概率再委派第四次（它不知道前面失败过几次——每次的收据是独立的）。

**建议**：在收据里带上「同一个 agent + 同一个 task 在本会话已失败 N 次」；超过阈值（如 2 次）直接在
工具结果里建议「换个做法或自己来」。这条也顺带缓解 S8 的费用闸缺失。

### E5 · 兜底定义的双重标准：`general` 的 `tools: null` = **全集**，含 `computer_action`

`agent-defs.ts:93-107` 要求**用户写的**定义必须显式列 `tools`（缺了就报「frontmatter 缺 tools：
请显式列出可用工具」）；而内建兜底 `general`（`:140-142`）用 `tools: null` ⇒ 拿到**全集**
（`subagent.ts:521-522`），包括 `bash`、`computer_action`（控制用户桌面）、全部 MCP 工具。

于是「默认工具集」这个听起来温和的名字，实际是「一个 fresh 上下文、由模型**自主发起**的子代理，
默认能操作你的桌面」。这与「子代理存在的意义是隔离」以及上面的「请显式列出可用工具」是矛盾的。

**建议**（二选一，倾向前者）：① `general` 显式列一份默认安全集（读 + 检索 + 写，**不含 `computer_*`**，
`bash` 是否含需要产品拍板）；② 若保留 `null`，至少在设置页与工具描述里明说「= 当前全部工具，含电脑控制」。

## 5. 收束：一个架构主张

三功能的问题不是「三个功能各自有 bug」，而是**同一个机制被写了三遍、且三遍的完成度不同**。
它们共享的东西比看上去多得多：

- 都是**两级发现**（项目级 + 用户级，同名项目级胜出）；
- 都要**如实告知遮蔽 / 冲突 / 解析失败**（技能已区分跨来源与同目录，子代理还没）；
- 都要**热更新写回**（技能 `setResources`、MCP `setTools`+heal、子代理没有）；
- 都要**一条状态视图 + 一条事件通道**（技能已把状态从事件通道挪走，子代理还没有）；
- 都是**隐式信任通道**（来自磁盘、进系统提示词），都需要「装了什么、坏在哪里」可见。

**建议的收敛方式不是大重构**（体量闸与风险都不允许），而是先做三件小对齐：

1. **契约对齐**：三者的「对外现状」类型统一到同一组字段（`name` / `source` / `status` / `error` / `disabled` / `diagnostics`）。
   今天是 `ViewSkill` 有 `source`、`McpServerView` 没有、子代理干脆没有类型。
2. **装载器对齐**：把「两级目录 + 同名取舍 + 遮蔽归因」抽成一个 shared 的纯函数
   （`dedupeByName` + `ShadowedSkill` 已经在技能侧被单测钉住了，直接抽出去给子代理用，
   **顺便消掉 S6 里那句假话**）。
3. **热更新对齐**：统一成一条命令形态（`xxxRescan` / `xxxReload` → 换容器 → 写回 harness → heal **所有 lane**
   → 广播到该项目所有活 worker）。MCP 与技能已经各写了一遍同构实现，第三遍（子代理）照抄即可，
   然后把三者的 heal 范围统一修正（S2）。

⚠️ 动手前请重读 `AGENTS.md` §1.4（体量闸：`worker/entry.ts` 与 `main/session-manager.ts` 零余量，
新逻辑必须进新文件、且要同时搬走等量旧代码）与 §3.5（先读代码确认现状）。本报告的每一条修法
都应落在 `worker/lib/*` 或 `shared/*` 的新模块里，`entry.ts` 只留一行委托。
