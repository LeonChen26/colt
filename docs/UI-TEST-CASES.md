# Colt · UI 测试用例（逻辑漏洞与合理性专项）

> **定位**：面向**界面逻辑**的测试用例集，目标是找出「逻辑漏洞」与「不合理处」，不是复述功能清单。
> **读法**：§二 是**已核实的疑似缺陷**（有代码位置），先看它；§三 是用例正文，按区域组织；§四 是现有冒烟的覆盖空白；§五 是执行建议。
> **不重复**：冒烟（`src/dev/smoke/`，见下）已覆盖的正向路径**本文一字不写**——重复正向用例只会让真问题更难被发现。
> **上游真源**：界面区域与规则 → `docs/UI-REGIONS.md`；失败如何呈现 → `docs/ERRORS.md`；冒烟与命令 → `CONTRIBUTING.md`；纪律 → `AGENTS.md`。

## 一、测试策略与判定口径

### 1.1 两类目标

| 类 | 代号 | 判据（出现任意一条即算命中） |
|---|---|---|
| **逻辑漏洞** | `L` | 状态机不一致（同一状态两处表达不同）／竞态（事件顺序改变结果）／**乐观更新无回滚**（界面已改、后端失败、界面不回退）／**静默失败**（失败与「合法地什么都没做」在界面上无法区分）／**静默截断**（只给前 N 条却不说还有更多）／**丢输入**（用户敲的内容被吃掉且不明显）／**死控件**（点了合法地毫无变化、也无说明）／**假绿灯**（断言/提示必然为真，包括「恒定值读数」）／边界未定义（0 条 / 1 条 / 上限 / 上限+1 / 中途切换）／**计数撒谎**（显示的数与数据源不同源） |
| **合理性** | `R` | 归属与命名（功能落在不符合它回答的问题的区域、名字暗示不存在的回路）／**反馈落点**（提示不在用户动手的位置）／认知负担（同一件事两套口径却不解释、同一动作两种契约）／可发现性（唯一出口被藏起来）／空态是否区分「真的空」与「还没到」 |

### 1.2 严重度

| 级 | 含义 | 例子 |
|---|---|---|
| **S1** | 丢用户输入 / 界面持续撒谎 / 阻塞态无出口 / 数据或会话被破坏 | 输入被静默吃掉、卡片消失但 lane 仍阻塞 |
| **S2** | 功能不可用或规则破损，用户会当成「产品坏了」 | 提示看不到、点了没反应、同一动作两种行为 |
| **S3** | 观感 / 文案 / 边角，不影响主流程 | 口径不一行、空态文案含糊 |

### 1.3 落地方式（与现有资产的分工）

| 标记 | 含义 |
|---|---|
| `SMOKE:<mode>` | 可用现有冒烟框架实现（`src/dev/smoke/modes/<mode>.ts`）：`run()` 在渲染层真派发事件 + 读主进程状态，逐条计数断言。**首选**——能验截图看不见的状态 |
| `UNIT:<文件>` | 纯函数边界，进 `tests/*.test.ts`（如 `lib.test.ts` 的 `messageWindow` / `slashCommand` 两节） |
| `RENDER` | 只验渲染层 DOM / 几何量，可用 `SMOKE:perf` 或 `dock` 的轻量段 |
| `MANUAL` | 需人工（输入法、拖拽、系统通知、真实窗口遮挡） |
| `REVIEW` | 读代码即可定论，不需要跑（用于「这条规则有没有守卫」） |

**纪律（写用例前先读，违反就会产出假绿灯）**：
- 断言要按**不变量**写（「逐像素相等」），不是「会变高」——只验「会变」不验「相等」等于没验（`ERRORS.md` §五.4）。
- 探针要认**区域自己的标记**（`data-*`），不用 `parentElement` / `children[i]` / class 碰运气（`AGENTS.md` §五⑫）。
- **不许断言内核的错误字符串**，只认 `net::ERR_` 前缀；写剪贴板前先 `window.focus()`（`ERRORS.md` §五.1/2）。
- 用例红了**先怀疑判据与接入方式**，再怀疑产品（`AGENTS.md` §1.2）。
- 测试装置**不得有副作用**：打桩只记账、不转调真实现（否则真计费、写用户数据、往真实会话塞假消息，`AGENTS.md` §五⑩）。

## 五、执行建议

### 5.1 优先级（按「用户会当成产品坏了」的程度排）

1. **第一批（S1，先做）**：UI-IN-02（运行中命令吃掉输入）、UI-IN-06（起手态报错跳位）、UI-CV-14（提问卡键冲突）、UI-CV-15（阻塞卡失败回滚）、UI-CV-03（浮动段漏更新）、UI-X-01（提示落点总验收）。
2. **第二批（S2，规则破损）**：UI-IN-03/04（附件静默）、UI-CV-09/10（搜索截断与 ESC）、UI-LB-03/UI-X-06（区域禁令断言化）、UI-SB-01/05/06（左栏三个入口）。
3. **第三批（S3 + 合理性）**：其余全部；`R` 类用例可与人工评审合并执行。

### 5.2 落地方式的选择

- **能写成冒烟的，一律别只写人工**：本仓的教训是「肉眼看不出的缺陷」（44px 图标条、逐像素对齐、必然为真的断言）——人工评审恰恰抓不到。
- **纯函数边界进单测**（`tests/lib.test.ts` 已有 `messageWindow` / `slashCommand` 两节，按同样风格追加）。
- 不调用模型的模式（`fixture` / `dock` / `perf` / `ask-user` / `skills-reload` / `memory` / `subagent`）优先承载新用例；**打模型的模式只用于「模型真的会这样吗」这一类问题**。

### 5.3 每条用例的完成定义

1. 先写**红**（能在当前代码上失败的断言），再决定是「产品缺陷」还是「用例判据错」——**用例红了先怀疑用例**（`AGENTS.md` §1.2）。
2. 修完跑 `npm run typecheck && npm test`，再跑该模式的冒烟，**条数以运行输出为准**。
3. 用例里出现的每个「期望值」要么现算、要么有 oracle，**不许写死像素/条数**（`AGENTS.md` §五⑥/⑬）。

### 6.4 实证过程抓出的**用例自身**的假绿灯（方法教训）

三条全是 `AGENTS.md` §五⑫ 那一类「**必然为真的断言**」——它们不会红，只会静静给出错结论：

1. **「起手态消失了」** 第一版是假绿灯：前提没建立时 `data-conv-start` 本来就不存在，「消失」必然为真。修法：**前提失败就不执行该段**，且把前提的三个条件（`start / opening / error`）一起打进日志。
2. **「`+` 菜单 ESC 能关」** 第一版同样必然为真：选择器 `[data-dock-menu-root] button` 找不到元素（那个标记挂在**按钮自身**上），菜单根本没打开。修法：选择器写成 `button[data-dock-menu-root]`，并把「找到按钮 / 菜单在 / ESC 后仍在」三个读数都打出来。
3. **「滚到顶部就能看到」** 第一版对照失败：设完 `scrollTop` 再由另一段代码读几何量，中间被产品的滚动逻辑改了。修法：**在同一个表达式里**设位置并立刻量。

> 这正是 UI-MT-01 要的东西：每条关键断言都要能回答「它在什么情况下会**不**成立」。上面三条第一版都答不上来。

### 6.5 二次复核（不同判据 + 对抗性检验，2026-09-25）

> 复核的规矩：**不重跑同一条断言**。要么换一个**不同的量**证明同一结论，要么**主动去证伪**——
> 「会不会别处其实能看到？」「会不会这条通道本来就是坏的，所以不算缺陷？」
> 下面 R1~R6 共 **15** 条断言，全绿。

| 项 | 换了什么判据 | 对抗性检验（找「有别的机制兜住」） | 结果 |
|---|---|---|---|
| **D1** | 不看 rect 的绝对值，改验**位移等式**：滚到底 / 滚到顶两个位置读同一元素，`位移 6256px ≈ 容器可滚量 6256px`——说明它就是**内容流顶部的普通块**，滚动是它不可见的唯一原因 | ① `[data-conv-error]` 全页只有 **1** 个；② 错误文案在**全页面只出现 1 处**（Live Bar / toast / 侧栏都没有）→ **没有兜底载体** | 成立 |
| **D2** | 不只跑一次，**再跑 3 次**看是不是偶发；并读**图标按钮的 `disabled`** 做两入口对照 | —（输入被吃这件事没有「别的机制」可兜） | 3/3 稳定：每次都「输入=空 / 派发=0」；图标按钮运行中 **disabled=true** → **同一件事两条入口行为不一致** |
| **D3** | 加验**粘贴图片**能不能收下（若也收不下，那性质就是「paste 通道整体坏了」，另当别论） | 粘贴图片 → **1 张，正常收下** → 通道是通的，缺的确实只是「非图片的提示」；再验粘贴非图片时附件数不变、提示为空、**输入框也没变** | 成立（是「静默」而不是「坏」） |
| **D4** | 换另一条触发路径：**先拖 3 张、再拖 2 张**（首轮是一条消息里拖 5 张） | — | 3 → 4（封顶），两次都无提示 |
| **D7** | 读 `document.activeElement` 当**直接证据**（而不是只看 ESC 效果）；并验「点浮层外到底关不关」 | 点浮层外 → **不关**（`mousedown` 派发到会话区，浮层仍在）→ **不存在外部点击关闭、也没有遮罩层**；代码层复核：该组件里没有 `useEffect` / document 级监听 | 成立（ESC 是唯一键盘出口，且看事件目标在不在浮层内） |
| **D10** | 验**持久性**（连续 3 次推「无消息」视图）+ 找**恢复条件** | 代码层复核：`setError(null)` 全在显式操作路径上，**没有任何定时器清除** → error 会一直挂着；恢复只能靠「做一次成功操作」——实测做完后起手态回来 | 成立 |

**复核的结论**：六条全部**再次确认**，且每条的「兜底机制」都被找过一遍——**找不到**。

### 6.6 复核中又抓到的三处**用例自身**的缺陷（比缺陷本身更值得记）

它们的共同症状是：**红的位置对，红的原因离真相很远**（差点被误读成产品 bug）：

1. **「搜索」按钮是 toggle**：进 R5 时浮层已开着（D7 段结尾的状态），我又点一次「搜索」→ 把浮层**关掉**了。于是「前提：焦点在浮层内」+ 两条 R5 断言同时红。修法：进入该段前先**显式关闭浮层**并断言「确实关着」。
2. **用「发一条普通消息」去清 error**：它能清，但会让 `promptOrReconnect` 的桩记 1 条 → 与「本模式不打模型（实发 0 条）」断言撞车。修法：改用 `/compact`（同样会 `setError(null)`，且只记账）。
3. **把打桩提前还原了**：D2 段末尾我把 `compactOrReconnect` 还原成真实现，导致 R6 的 `/compact` **真走了 worker**，worker 报「没有可压缩的内容：会话还没有消息…」→ 那句错误被 `setError` 设回去，「清 error」**必然失败**。修法：桩统一只在 `finally` 里还原。

> 这三条都是「**测试装置的接线问题**」，不是被测代码的问题（`AGENTS.md` §1.2）。
> 第 3 条尤其值：若不把 `/compact` 之后的三份读数（输入框 / 桩计数 / error 文案）一起打出来，
> 它看起来就是一条「产品清不掉错误」的假 bug。
