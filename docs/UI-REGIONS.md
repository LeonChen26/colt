# Colt 界面区域定义

> **作用**：约束后续 UI 修改。任何新增/移动功能，先在此找到归属区域，再动手。
> **定位**：开发者自用的桌面 Agent 工作台，Work 模式。
> **边界**：只定义**结构职责**，不定义视觉细节。

---

## 零、总原则

**1. 一个区域只回答一类疑问。** 功能回答的疑问与所在区域不符时，应当搬家，不是就地妥协。

**2. 区域按「视角」分层。** 全局 / 会话级 / 运行态 / 外部世界——不同视角的信息不混放。

**3. 只读区不承载操作，操作区不承载观测。** 这是最容易被破坏、最需反复检查的一条。

---

## 一、骨架与视角

```
┌─────────────────────────────────────────────────────────────┐
│ ① 标题栏                    视角：系统（非产品设计）          │
├──────────┬──────────────────────────────┬───────────────────┤
│          │ ② 会话头    视角：会话级      │                   │
│ ③ 左栏   ├──────────────────────────────┤ ⑦ 右栏            │
│ 视角：   │ ④ 会话流    视角：会话级/时间 │ 视角：外部世界     │
│ 全局     ├──────────────────────────────┤                   │
│          │ ⑤ 输入区    视角：会话级      │                   │
│          ├──────────────────────────────┤                   │
│          │ ⑥ 状态栏    视角：运行态      │                   │
└──────────┴──────────────────────────────┴───────────────────┘
```

**结构概括**：**导航 | 叙事 | 现场**。

- 左栏是**入口**（去哪、做什么）
- 中栏是**主线**（你和 agent 的过程）
- 右栏是**副产物**（agent 干活时外界的样子）

---

## 二、区域定义与规则

### ① 标题栏 · 系统级

| 项 | 内容 |
|---|---|
| **回答** | 我在哪个应用、能否操作窗口 |
| **承载** | 侧栏开关、搜索、菜单、窗口按钮 |
| **禁止** | 任何产品功能 |

> **规则 ①-A**：这里的一切属于操作系统/Electron 层面，设计决策不在此处做。

---

### ② 会话头 · 会话级标识

| 项 | 内容 |
|---|---|
| **回答** | 我在哪个任务里？哪些操作是针对**这个会话**本身的？ |
| **承载** | 任务标题、会话级操作（分享、复制）、**会话上下文（cwd / 分支）** |
| **禁止** | **运行态操作**（停止/暂停）、**发送参数**（模型、权限模式） |

> **规则 ②-A**：判据是「这个操作在会话不运行时还成立吗？」
> 成立（分享、复制）→ 属于这里。不成立（停止）→ 属于 ⑤。

> **规则 ②-B**：会话的**上下文**（工作目录、分支）必须在此可见——这是"我在哪干活"的核心信息。

---

### ③ 左栏 · 全局导航

| 项 | 内容 |
|---|---|
| **回答** | 我能去哪？我有哪些任务？ |
| **承载** | 模式切换、功能入口、项目/任务列表、用户区 |
| **禁止** | 会话内的任何状态 |

**内部必须分两层**（当前设计混淆，需区分）：

| 层 | 内容 | 语义 | 视觉权重 |
|---|---|---|---|
| **L1 模式** | Work / Code / Design | 改变**整个应用**的形态 | 重 |
| **L2 导航** | 新建任务 / 插件市场 / 模板库 / 自动化 / 办公助理 | **跳转**到别处 | 轻 |

> **规则 ③-A**：L1 与 L2 语义不同，**不可同权重并列**。
> L1 是上下文切换（我换了工作模式），L2 是页面跳转（我去看别的功能）。
>
> **状态（2026-09）**：L1（Work/Code/Design 模式切换）与 L2（新建任务/插件市场/
> 模板库/自动化/办公助理）**均为计划中功能，尚未实现，短期不做**。
> 当前产品的左栏是「项目 → 会话」两层列表 **+ 会话分支树面板**（下半区，按会话展示分支、
> 可点击跳转，见 `features/BranchTree.tsx`）；L1 / L2 本身仍无适用对象。
> 待功能落地时再执行本规则。

> **规则 ③-B**：任务列表是**跨项目、跨会话**的，属于全局视角，不随当前会话变化。

---

### ④ 会话流 · 叙事主线（核心区域）

| 项 | 内容 |
|---|---|
| **回答** | 我们聊了什么？它做了什么？ |
| **承载** | 思考轨、用户消息、Agent 回复、**工具卡**（内嵌 diff）、授权卡 |
| **顺序** | **严格按时间线性排列** |
| **禁止** | 非本次会话的信息、跨会话汇总 |

**必须承载的信息类型清单**（每类一个组件）：

| 类型 | 组件 | 来源 | 优先级 |
|---|---|---|---|
| 推理过程 | 思考轨 | `ThinkingRail` / `ThoughtBlock` | P1 |
| 正式回复 | Markdown | `Markdown` | P0 |
| **工具调用** | **工具卡** | `ToolCard` | **P0（最高频）** |
| 权限阻塞 | 授权卡 | `ApprovalCard` | P0 |
| 文件变更 | **工具卡内嵌 diff** | `MessageList.tsx` 的 `ToolCard` | P1 |

> ⚠️ **订正（2026-09）**：此处原写「变更卡 / `ProjectChanges`」。`ProjectChanges` 实为**主区整页**
> （项目级、跨会话的改动汇总，由 ① 的「改动」按钮打开），**不在 ④**——④ 明确禁止跨会话信息。
> ④ 里承担「文件变更」的是**工具卡内嵌的 diff**，它也是「点文件路径 → 下钻预览」的入口。

> **规则 ④-A**：**信息密度必须可调**。工具卡默认折叠成一行（图标 + 名称 + 路径/命令 + 增删 + 耗时 + 状态），展开才显示 diff / 输出 / 截图。
> 依据：自用场景需要"扫一眼知道发生了什么"，而非"每次都被细节淹没"。

> **规则 ④-B**：**叙事顺序不可打乱**。推理在结论前，工具调用在结果前，授权卡在它阻塞的那个时刻。

> **规则 ④-C**：工具卡是**出现频率最高**的元素（每轮多个），其设计质量直接决定"能否看懂它在干嘛"。**不可省略、不可简化成一行纯文本**。

> **规则 ④-D**：工具卡图标必须**语义化**（read / edit / bash / browser / computer 各不同），不可统一用扳手。

---

### ⑤ 输入区 · 交办

| 项 | 内容 |
|---|---|
| **回答** | 我要它干什么？**用什么参数**？ |
| **承载** | 输入框、附件、**模型选择**、发送/停止 |
| **禁止** | 运行状态观测（那属于 ⑥） |

> **规则 ⑤-A**：判据是「这是**发送这条消息的参数**吗？」
> 是（模型）→ 属于这里。不是（上下文占用、心跳）→ 属于 ⑥。

> **规则 ⑤-B**：**停止/中断**属于这里。理由：它是"控制本次运行"的操作，与"发起本次运行"（发送）同源。

> **规则 ⑤-C**：窄宽度时**先折叠文字标签，再考虑换行**。发送按钮永不收缩、永不被挤出。

> **规则 ⑤-D**（2026-09 修订）：**权限（审批）模式在此区域呈现**——它属于「发送这条消息的参数」（同 ⑤-A），
> 位置是输入工具行右侧的下拉。
> 历史：曾写作「暂不在此区域呈现」，后由实现确定归属（见 §四 的处置表）。

> **规则 ⑤-E**（v1.44）：**斜杠命令的候选浮层**属于这里，且**必须是浮层、不占工具行的常驻宽度**。
> 理由有二：一是 ⑤-C 已经规定了工具行在窄宽度下的行为，而那一行已有 4 个控件、还带着一条
> 「卡片不能被裁」的回归，再挂一个常驻控件就等于把问题推给它；二是命令的**名字本来就要打在输入框里**，
> 提示贴着输入框长才自然（对齐 ACP 那种「输入 `/` 弹命令」的直觉）。
> 硬约束：**浮层只在候选真的存在时才出现**——否则用户每次贴 `/usr/local/bin` 这类路径都会被一个
> 空菜单打扰（`slashCandidates` 的前缀规则与「整条命令已敲全就不弹」都是为此）。

> **规则 ⑤-F**（2026-09）：**斜杠命令共三条，分两类语义**，判据全在 `lib/slash-command.ts`（纯函数、有单测）。
> - **零参数**：`/compact`（压缩上下文）、`/memory-tidy`（整理沉淀的记忆）——必须**独占整条输入**
>   （`"/compact"` 或带尾空格都算，`"/compact 一下"` 不算），**不做前缀匹配**：
>   否则用户想发「用 /compact 手动压缩」这句正文会被当成命令吞掉（v1.34 的教训）。
> - **带参数**：`/skill <名字> [额外指示]`——只能前缀匹配，故加两道阀限制代价：
>   命令字须**整段等于** `skill`（`/skills`、`/skillfoo` 都不是命令），且后面须真有**非空名字段**。
> - 名字不存在时**不回落成普通消息**，而是**就地拦下**并给出同一句话（文案在 `@shared/skill-error`，
>   渲染层与 worker 共用同一份）——「敲了没反应」比报错更伤信任。

### ⑥ 状态栏 · 运行态观测

| 项 | 内容 |
|---|---|
| **回答** | 现在什么情况？**它还活着吗**？ |
| **承载** | 上下文占用、成本、心跳（已耗时 + 最后活动）、stale 警告 |
| **禁止** | **任何操作**（按钮、开关）、发送参数 |

> **规则 ⑥-A**：**只读区不放操作。** 本区域最容易被破坏的规则。
> 反例：曾有中断按钮、模型选择器、会话级模式选择器置于此，均已移除。

> **规则 ⑥-B**：**必须每秒走字**。心跳的意义在于"数字在动 = 它活着"。停止走字本身即信号。

> **规则 ⑥-C**：**超时不许伪造活动**。超过阈值无事件时**如实**提示，**不可用转圈动画假装在忙**。
> 实现口径（2026-09 校准）：心跳常显「最后活动 Ns 前」；超过 `STALE_IDLE_SEC = 30` 秒无事件时
> 该读数转琥珀，并追加「似乎卡住了，可中断」。提示的是「没动静」这件事本身，
> 不把它改写成「还在忙」的任何说法——也不给用户一个假的进度。

> **规则 ⑥-D**（2026-09 落定）：运行态之外**必须给出明确的状态**，不留空。
> 状态段由 `running` + 最近一轮终态（`ConversationView.lastRun`）推出，共四态：
> 运行中（绿点脉动）/ **已中断**（灰点 + 文案）/ **已失败**（红点 + 文案 + 一行截断的 error 摘要，悬停看全文）/
> **空闲**（灰点 + 「空闲」）。
> - 只有**中断**与**失败**单独留一行：正常跑完（`completed`）与「还没跑过」一样回到「空闲」——
>   状态条不该为一次正常的结束留痕。判定是纯函数 `lib/format.ts` 的 `runStateOf`（有单测）。
> - 终态取内核 `LaneSnapshot.lastResult` 且**只认 `kind === "run"`**（压缩 / 导航的终态不答「我交办的事」这一问）。
>   ⚠️ **别用 `faulted`**：那是 harness `fault` 事件的会话级硬故障、内核从不复位它。
>   （该字段已从 `ConversationView` 删除，见 `ERRORS.md` §三；判据仍是 `runStateOf`。）
> - 状态是**电平**：结束态一直留到下一轮跑完，不是一闪而过的提示。
> - 颜色只是**辅助**，每个态旁边都有文字（v3 §5「颜色必须配文字」）。
> - 已知限制：`lastResult` 是 lane 生命期的记录，worker 被空闲回收后重建（切会话 / 重启）会丢 → 回落成「空闲」。

> **规则 ⑥-E**：位置在**输入区下方**。理由：与"交办"动作相邻，发完即可观察状态。

### ⑦ 右栏 · 工作区（Workspace）

| 项 | 内容 |
|---|---|
| **回答** | Agent 正在操作的**对象**长什么样？以及我想看的任何附属内容 |
| **定位** | **一个可插拔的容器**，不是某个专用栏 |
| **默认视图** | **正在处理**（agent 正在读 / 改哪些文件） |
| **其他视图** | 浏览器、Markdown 阅读器、文件浏览……**不限个数** |
| **宽度** | **由用户拖拽决定**（220px ~ 窗口中栏留 360），视图切换不覆盖 |
| **禁止** | 会话叙事（那属于 ④） |

**定义要点**：右栏**就是工作区**，「正在处理」只是它的默认视图。

| 视图类型 | 内容 | 对应疑问 |
|---|---|---|
| **正在处理**（默认） | agent 正在读 / 改哪些文件 | 它在本地碰什么 |
| **外部世界** | 浏览器页面、URL、console / network / downloads、用户自己的前进 / 后退 / 刷新、装不下时的「适应宽度」 | 它在网上操作什么 |
| **阅读** | Markdown / 文本阅读器 | 我想看什么内容 |
| **文件** | 系统文件浏览 | 项目里有什么 |
| **附属内容**（A3-5） | 会话统计（原用量历史）、审批规则 | 这次会话花了多少、被放行/拦了什么 |

> **代码现状与范围（2026-09）**：页签只有四个 kind——**正在处理（默认）/ 浏览器 / 统计 / 规则**。
> 「阅读 / 文件」的范围经产品与架构双向审视后**已收窄**（决定记录见 `NEXT-PHASE.md` A3）：
> **不做整项目树**——右栏是「现场」，「项目里有什么」是 IDE 的问题，不是本栏的问题。
> 落地形式是**「点文件路径 → 预览」**（A3-2，2026-09）：入口是消息流（④）里工具卡的副标题
> （仅当副标题就是该工具操作的文件时才可点）。预览按类型分流：
> `.md` 走 Markdown 渲染；**其余文本按扩展名认语言**（`renderer/src/lib/code-lang.ts`）后交给
> highlight.js 着色 + 左列行号，**认不出就原样等宽、不猜**；图片给 dataUrl、二进制与过大只给提示（**不做半截渲染**）。
> 语言映射只列 common 包里注册过的语言（给一个包内没有的名字＝回了纯文本），这条由单测逐条核对。
> **⑦-G 第四步（v1.32）之后，这些内容不再各占一个页签**：预览是「正在处理」下钻的**内容层**，
> 而原先「范围 A：本次动过的文件」那棵树（A3-4）升级成了同一处的**清单层**
> ——按目录**一层**分组（不是可折叠树），同一文件多次编辑折成 `×N`，行上带 `+a −b`；
> 清单只列 `fileChanges` 且**排除不可预览的越界路径**，并把隐藏了几条如实写在底部（约束 ⑦-4）。
> 原「文件」视图的双栏（预览左 + 200px 树右）与窄栏容器查询（`styles.css` 的 `.file-view` / `fv-tree`）
> 随之删除——不再有需要让位的第二栏。
> **页签模型已落地为「实例列表 + `activeId`」**（A3-1，2026-09），页签行与折叠图标条都按实例列表渲染；
> **页签可关闭 + 「+」新增视图已落地**（A3-3，2026-09）——「可关闭」与「菜单里能打开」是**同一集合**
> （清单由 `closable` 推导），故结构上不存在「关了回不来」；菜单**只列产品里真有的视图**
> （⑦-G 后为 `browser / usage / rules` 三项；终端 / 任务摘要仍未实现，不入菜单，避免死菜单项）；
> 「浏览器是否多开」见 A3 的「事 B」。
>
> **两个观测 / 管理面板已迁入本容器**（A3-5，2026-09）：「统计 / 规则」由**中栏浮层**
> 改为 ⑦ 的**可关闭页签**——依据正是本栏定义里的「**以及我想看的任何附属内容**」与「其余视图不限个数」。
> 迁入后**只有页签这一个载体**：面板自身不再有「收起」（关闭交给页签的 ×），
> ② 会话头的两个入口与「+」菜单都只是打开同一页签的快捷方式。
> 这消除了「改动面板 vs 代码变更视图」这类**同一件事两处实现**（⑦-G 最终把两者合成下钻），
> 也让中栏只留叙事主线（④）。
> 页签清单见 `WorkspaceDock.tsx` 的 `DOCK_KIND_META`；宽度是**全局统一值** `DOCK_DEFAULT_WIDTH`（见 ⑦-B）。
>
> **浏览器页签底部有「观测抽屉」**（B2，2026-09）：控制台 / 网络 / 下载三份观测，数据就是
> 本栏「外部世界」视图要回答的那一问。它读的是主进程 `CaptureBuffer`——与 agent 的
> `browser_read` **同一份**缓冲，不存在「界面说的和模型看到的不一样」。抽屉**属于浏览器视图内部**，
> 不另立页签：它回答的是「这个页面怎么了」，脱离页面就没有意义（与 ⑦-C「视野跳跃为零」一致）。
> 抽屉占页面区域的高度，收起/展开经 ResizeObserver → `browser.bounds` 同步给原生视图。
> **行是概览，点开才是全貌**（N1，2026-09，v1.33）：一行装不下完整 URL / 绝对路径，
> 原先只能靠原生 tooltip 兜底；现在点一行在下方展开「字段表 + 复制」，
> `URL` / 路径上的 tooltip 随之撤掉（同一件事不留两个入口）。
> 字段映射抽在 `lib/observe-detail.ts`（纯函数，有单测）；详情段落带自动滚入可视区
> （正文只有 132px 高，不滚进来就是「点了像没反应」）。
> 实现见 `features/Conversation/ObserveDrawer.tsx`。
>
> **浏览器页签顶部有「后退 / 前进 / 刷新」**（B1，2026-09）：由**用户**发起，与 agent 的 `browser_act`
> 是两条链路——那条走审批（裁决的是模型给出的入参），这条没有模型参与、没有可裁决的对象，**不走审批**；

#### ⑦ 实现约束（用户不可感知，但代码必须遵守）

**约束 ⑦-1：「不限个数」指的是页签，不是同时挂载的 WebContentsView。**

各视图的资源成本差异极大：

| 视图 | 成本 |
|---|---|
| 正在处理 | 纯 DOM，几乎为零 |
| Markdown 阅读器 | 中等（取决于文档大小） |
| 浏览器 | **一个独立渲染进程，几十到几百 MB** |

> ⚠️ **订正（2026-09）**：表里的「Markdown 阅读器」**从未落地**（现有 4 个 kind 里没有它）；
> 「正在处理」现在是**容器 + 下钻三层**（清单 / diff / 文件内容）的总称，成本取决于所在层。

因此：

- **页签可以很多**（轻量，只记录状态与位置）
- **同时存活的重型视图必须限制**（建议最多 2～3 个）
- 超出的应**挂起**（销毁 WebContentsView，保留页签与 URL，切回时重建）

**约束 ⑦-2：懒创建必须到页签层，不只是浏览器。**

现有 `browser-host.ts` 已是会话级懒创建；接入工作区后应下沉到**视图级**——
未激活的页签不创建 `WebContentsView`（对齐 ⑦-B）。

**约束 ⑦-3：视图销毁必须可回收。**

`browser-host.ts` 的注释已记录过这个坑：
> 新窗口一律不开：默认行为会生出一个**不受本类管理**的窗口——读不到、
> `disposeAll` 也回收不掉，而 agent 后续的 `snapshot`/`text` 仍停在旧页面上，
> **表现为「点了没反应」**。

多视图后同类风险会被放大：**任何视图都必须登记在容器里**，
能随会话关闭 / 页签关闭 / 挂起而正确销毁，不留孤儿进程。

**约束 ⑦-4：读文件视图的「根」只能由主进程推导；路径必须落在根内。**

> **载体已变（2026-09）**：原为「文件」页签，v1.32 起是「正在处理」下钻的**内容层**
> （`panels/FilePreview.tsx`）。约束本身不变。

渲染项目内文件的内容层，路径来自会话视图（agent 刚碰过的文件）。根由主进程按
`sessionId → 项目 → root_path` 查出，并做三层校验（`resolve` 后仍须落在根内 →
`realpath` 之后**再判一次** → 大小上限 + 二进制判定）。**绝不能让渲染层指定读哪个根**——
渲染层会渲染 agent 生成的 Markdown，一旦放开等于把任意读盘能力交出去。

路径**相对 / 绝对皆收**（工具入参里的 path 由模型给出，可能是绝对路径），但都必须落在根内；
**越界判断是纯字符串运算，先于任何 fs 访问**——根外的绝对路径不会去碰磁盘，因此不会变成
「某路径存不存在」的探测口。纪律见 `NEXT-PHASE.md` §7，实现见 `src/main/file-read.ts`。
另注：`sessions` 表**不存 cwd**，根只在 `projects.root_path` 上。

### v1.34 —— `/compact` 斜杠命令：手动压缩上下文（2026-09）

> 依据：用户要求「实现一个手动上下文压缩的命令」。
>
> ⚠️ **动手前先读代码纠正了一处前提**：压缩**全链路早已存在**——

**① 命令识别是纯前端本地判定（`lib/slash-command.ts`）**

### v1.36 —— ⑦ 的「本次改动」显示**净值**：多次改动看的是「最终改成了什么」（2026-09）

> 依据：用户反馈「有每次修改的内容，但如果多次修改、每次是分开的，就不知道当前文件最终是改了什么；
> 比如改完又回退了，现在的逻辑就很难体现」。

**根因：只存了「每次改了什么」，从没存「改之前是什么」。** `ViewFileChange` 只有 `patch` /
`addedLines` / `removedLines`（worker 在 `after_tool` 上报，那一瞬原文已被覆盖，补也来不及），
于是卡片上的 `+a −b` 只能是**逐次相加**：改了又退回原样的一串编辑相加是 `+10 −10`，
而文件其实一点没变——照相加显示**等于撒谎**。没有基线，「最终是什么样」也无从谈起。

**① 基线：worker 在工具执行前读一次**（`worker/lib/baseline.ts` + `before_tool` 闸门）
- 时机只有一处对：`before_tool`（等审批**之前**）。`after_tool` 时文件已是新内容，读到的只能是
  「改完的样子」——净值会恒为 0，而且**不报错**，只会让界面一直说「已还原」。
- 两种「没内容」必须分得开：`existed: false`（当时文件不存在 = 新建，净变化即整份新增）
  vs `text: null`（过大 / 二进制 / 读不了 = 算不出）。互相顶替就会各自说错话。
- 按路径去重、只在该文件**第一次**改动时随改动上报全文。

**② 落库与计算都在主进程**（`db` 的 `file_baselines` 表 + `file_changes` 两列、`main/net-change.ts`）
- `recordFileBaseline` 用 `ON CONFLICT DO NOTHING`：**只认最早那一份**。worker 被回收重启后
  不记得发过基线，会把「当时已经改过」的内容当基线再报一次——信它等于把会话前段的变化吃掉。
- 净值在**改动落库那一刻**算好写回该行（`setChangeNet`），界面因此不必每次重算、也不读盘。
  算不出写 NULL（不是 0），`listSessionFileChanges` 原样带出。
- 行级 diff 是新写的纯函数 `shared/line-diff.ts`（公共前后缀先砍、再对中间段求最短编辑脚本，
  矩阵过大退化成整块替换但**不丢行**）。没有引第三方 diff 库。
- 迁移 v8：旧库补两列 + 建基线表；**存量改动的净值为 NULL**，界面据此只显示逐次改动。

**③ 界面**：卡片 `/N` 与头部总账的 `+a −b` 一律换成**净值**
- 净 0 且**有结论**时明说「**已还原**」（与「算不出」严格分开）；算不出则**不显示数字**，
  改为在清单底部如实计数（`N 个文件未记录改动前的内容…`）——静默丢数据比不显示更可疑。
- `diff` 层多一档「**累计**」（与 `#1 #2 #3` 并列、不给编号）：现算「基线 → 当前」，
  故它答的是「这个文件最终被改成了什么」，哪怕中间有人在编辑器里手工动过；
  净值已知为 0 时**不问主进程**，直接给结论。`DiffView` 直接吃这份 patch，不为净值单写视图。
- 逐次的那对数字**没有消失**：它们仍在 `×N` 展开的历史行里——卡片看净值、历史行看逐次。
- 同一口径贯穿：清单卡片、清单头部、`FollowPanel` 总账的 `+a −b` 全部同源（`buildChangeList`）。
  ⚠️ 总账的「处 / 文件」两个数**未改口径**（仍是含项目外条目的原始计数，v1.32 定的），
  本次只动 `+a −b`。

**④ 新协议**：`file.netDiff`（`{sessionId, path}` → `ok | no-baseline | unreadable`）。
根与基线都**只由主进程**取（前者按 sessionId → 项目推出，后者来自库），渲染层仍不碰 fs。

### v1.37 —— 文件内容**按格式渲染**：`.md` 之外不再是一坨纯文本（2026-09）

> 依据：用户反馈「目前的文件展示，没有按照文件格式渲染」。

**根因：分流只做了两级——`.md` 走 Markdown，其余一律裸 `<pre>`。** 于是 `.json` / `.ts` / `.css`
在预览里既没有着色也没有行号，跟「打开的是哪种格式的文件」毫无关系；`.md` 之所以像被渲染过，
只是因为 `react-markdown` 恰好接了这一支。**不是分流坏了，是分流的另一半从来没写。**

**① 认语言：纯函数 + 一张白名单**（`renderer/src/lib/code-lang.ts`）
- 只认 `highlight.js/lib/common` 里**确实注册过**的语言。给一个包内没有的名字，调用方只能回落成
  纯文本——**等于白识别**，所以表里不列 scala / groovy / dockerfile 这些「应该有」的语言。
- **认不出返回 `null`，不猜**：猜错会把阅读者的注意力引到错误的着色上，与「不做半截渲染」同一条理由。
- Markdown **不在表里**：`.md / .mdx` 由 `FilePreview` 直接交给 Markdown 渲染器，两处都给就是打架。

**② 渲染**（`components/CodeView.tsx`）
- 左列行号整列拼成**一个文本节点**（不是每行一个元素）——大文件几万行时，几万个 DOM 节点比着色本身还贵。
  行号列 `position: sticky`，长行横向滚动时不被推走；**两列行高只在容器上写一次**，否则第 100 行会错开。
- 超过 30 万字符**放弃着色**（仍给行号）：highlight.js 是同步的，1MB 的文本上限能把渲染卡住几秒。
- 配色复用 `.md` 那套 `--color-code-*`（`styles.css` 的 `:is(.md, .code-view) .hljs-*`），
  同一段代码在助手回复与文件预览里不会出现两种颜色。
- 着色失败**不静默回落**：退回纯文本的同时 `console.error`——静默回落与「这个文件本来就没颜色」
  在界面上完全一样，一旦打包 interop 或升版本把调用方式弄坏，这里就是唯一的证据。

**③ 让「认出了什么」可见**：文件头多一枚语言名（`data-file-lang`）。颜色是主观的，语言名是可核对的。

**影响**：`FilePreview` 少一支裸 `<pre>`，其余分支（Markdown / 图片 / 二进制 / 过大）不变；
`highlight.js` 从**传递依赖升为显式声明**（此前只经 `rehype-highlight` → `lowlight` 间接引入）。

### v1.38 —— 思考等级成为**会话配置**（默认「高」），修掉「/compact 点了没反应」（2026-09）

> 依据：用户反馈「/compact 不生效」，并追问「compact 不生效和模型是否支持 thinking 有什么关系」。

**根因（经真实请求实测，不是推断）：那句「关闭思考」是我们自己发出去的。**
- Colt 从不设置思考等级 → 内核 `harness.js` 的 `thinkingLevel: options.thinkingLevel ?? "off"`
  兜底成 `off`；
- pi-ai 的 zai 兼容层见到 `off` 会**显式**写 `thinking:{"type":"disabled"}`，而 GLM-5.3-flash 对
  **不带工具**的请求直接 400；
- 手动压缩恰好是一条**不带工具**的请求 → 摘要生成失败 → `summarization_failed`（`kind=compaction`）
  → `/compact` 看起来「点了没反应」。主对话之所以一直正常，是因为它**带工具**，同一条
  `thinking:disabled` 被接受——所以「模型不支持思考」不是原因，**模型恰恰是「始终思考」**。

> 压缩算法本身是**内核自带**的（`pi-agent-core` 的 `harness/compaction/`）：切点、摘要、保留尾部
> 都在内核里，Colt 只负责入口、参数装配、失败翻译与提示。这次错的是**我们给它的参数**。

**① 默认值不能再是 `off`**（`shared/thinking-level.ts`）
- 界面只开放 `off | low | medium | high` 四档：其余档对多数 provider 会被钳制到相邻档，放出来
  只会让人以为选了 A 实跑 B；默认 `high`。
- 库里是 `NULL`（字段新增、从未选过）或历史脏值时一律回落到默认值，不把脏值透传给内核。

**② 存量会话必须显式覆盖**（`worker/entry.ts`）
- 内核的 `thinkingLevel` 种子**只对新建 lane 生效**，已存在的会话会沿用自己持久化的值——而老会话
  存着的是当年的 `off`（那时谁都没选过），正是 400 的源头。故打开会话时与内核当前值比对，
  有差异才 `setThinkingLevel`。
- 比对不是多余的：`setThinkingLevel` 不做等值短路，无条件调用会让每开一次会话都多一条配置事件。

**③ 不走内核的两条请求也得带上**（否则会「修好压缩、坏了放行」）
- **审批分析器**（`main/approval/analyzer.ts`）不走 harness，且同样**不带工具**——它一直在同一条
  400 上静默降级成手动确认。注意低层 API 收的是 `reasoningEffort`，不是 harness 那层的 `reasoning`。
- 会话级落库（`sessions.thinking_level`，迁移 v9）；**草稿会话**先记在草稿里，首次发消息落库时写出。

**④ 让「压缩失败」不再无声无息**
- 此前两条失败路径都不显眼：accept 阶段被拒走 `Result.err`，而摘要失败（最常见的密钥 / 网络 /
  模型错误）被内核结算成 `ok: true` + `status: "failed"`——只查 `Result.err` 依旧静默。
  现按 `_tag` / `code` / `status` 翻译成一句话（`worker/lib/compact-error.ts`），成功时给绿色横条
  并带上「压缩前约 N tokens」（`data-conv-compact-notice`）。

**⑤ 界面**：输入区 `/compact` 右侧、模型选择器左边加思考等级下拉；「不思考」保留但写明风险
（「始终思考」的模型会拒绝它，连带压缩与自动放行一起失败）。

**影响**：`/compact`、**自动压缩**（内核默认 `enabled: true, reserveTokens: 16384`，Colt 未覆盖）
与审批分析器三条链路共用同一套参数装配，改一处同时影响三者；会话多一列 `thinking_level`（迁移 v9，
旧库留 `NULL`）。

验收：`typecheck` / `build` / 单测 **557** 条（556 通过、1 跳过；新增「思考等级」6 条 + 「压缩失败
翻译」5 条 + 迁移 v9 1 条，后者断言存量会话为 `NULL` 而**不是** `off`）。**真实请求已实测**：同一

### v1.39 —— 三条「说不出来」的体验：等待授权 / 附件静默 / 页面装不下（2026-09）

> 依据：用户要求「从产品的角度继续分析我们的体验」。三条都是**状态确实存在、界面上却看不出来**。

**① 审批会「喊不到人」**（最要命的一条）
- 现状：审批是本产品唯一需要用户**立刻拍板**的状态（5 分钟不处置即自动拒绝），可窗口不在前台时
  既不闪任务栏也不发通知；侧栏那一行只显示「运行中 · mm:ss」，看不出它在等人。

- 修：`sessionManager` 在**待审列表变化时**派生提醒状态。`#emitPending` 是唯一同步点
  （入队 / 处置 / 超时 / 中断 / 崩溃清理都必经此地），在那里派生才不会出现
  「界面已清空、任务栏还在闪」这类两处状态打架。窗口未聚焦才闪任务栏 + 发系统通知，
  **不抢焦点**（用户可能正在别处打字，抢焦点等同于打断）；同一条 `toolCallId` 只提醒一次，
  记录按会话分组，待审清空即回收（否则跟着进程无界增长）。
- 侧栏新增「**等待你的授权**」（`App.tsx` 走全局 `approval.pending` 事件），**优先于「运行中」**显示：
  会话确实在跑，但 Agent 正卡在一个待批的工具调用上不动。
- Windows 的通知要求进程有 AppUserModelID，故补 `app.setAppUserModelId("com.colt.app")`
  （非 Windows 上为空操作）——不加的话开发态通知根本不显示，等于加了个「点了没反应」的入口。

**② 附件「没进来」是静默的**
- 现状：`addFiles` 对非图片直接 `return`——往输入框拖一个 PDF 什么都没发生，用户只会以为程序坏了。
  附件通道只承载图片（内核 `imageInput` 语义）**不是缺陷，没说出来才是**。
- 修：被跳过的非图片、超限的图片都汇总成一条提示，且**贴在输入卡片里**而不是顶部消息区：
  顶部那条 `error` 在消息滚到底时根本不在视野内，等于没说。图片照常进附件（不因加了提示而改变行为）。

**③ 最小窗口下内嵌浏览器被裁、且滚不回来**
- 先是**算清楚上限**：窗口 `minWidth: 1024`，右栏最多 = 1024 − 601（左栏 241 + 中栏下限 360）
  ≈ **423**；而固定宽度的站点（实测某搜索首页 768px）会被裁掉**且禁了横向滚动**——
  右边既没有滚动条也没有别的入口。要装下 768 得把 `minWidth` 抬到 1369，**会挡掉 1366 宽的屏**，故不抬。
- 于是改成「让它说出来」：主进程量一个「页面够不到的内容宽度」
  （`browser-scripts.ts` 的 `CONTENT_WIDTH_SCRIPT`），渲染层拿它与自己的区域宽比，
  装不下就在页面上方挂一条横条（`data-browser-clipped`），写明「需要 Npx / 可视区 Mpx」
  与唯一的出口（拖宽右栏 / 最大化窗口）；拉宽到装得下**自行消失**。
  **判据是算出来的，不是「栏一窄就报警」**——响应式页面在窄栏里会自己重排，
  那种页面永远不满足条件，也就不会挂上一条永远为真的灰条（持续撒谎的提示比没有提示更糟）。
- 两个**实测**出来的坑（都写进代码注释，别再踩）：
  ① 不要去遍历全元素求右边界——宽表格套在 `overflow-x: auto` 的壳里时，超出的是那个壳，
  用户滚那个壳就看得到；文档级 `scrollWidth` 天然不含这种内层裁剪。
  ② 不能拿 `documentElement.scrollWidth > clientWidth` 当「有横向滚动条」的依据：
  夹具页视口 219 / 内容 700、`<html>` 写了 `overflow-x: hidden`，而它照样报 700（**并没有被钳**）。
  照那个判据走会把「真的够不到」误判成「用户自己能滚」，于是永远不提示。
  改用「根 / body 的 `overflow-x` 是不是 hidden」判「用户滚不到」
  （`overflow: hidden` 只禁止**用户**滚动，脚本仍能改 scrollLeft，所以也不能靠「试着滚一下看动不动」）。
- 还有一条**静默失败**：`did-finish-load` 触发时 `isLoading()` 仍可能是 true（favicon 之类还在飞），
  只量一次会被挡掉且无人重试——`contentWidth` 一直是 0，页面真的装不下却永远不提示。
  故补有限次重试（3 次 × 500ms），仍不成还有下一次导航 / 尺寸变化兜底。
- `BrowserViewState` 从此多一个 `contentWidth`（**跨进程契约**，见 `ARCHITECTURE.md`）。

**影响**：`BrowserViewState` 加字段；主进程多两类提醒（任务栏闪烁 / 系统通知）；
`App.tsx` 多一个「等待授权」状态、`Conversation/index.tsx` 多一条卡片内提示、

### v1.40 —— 「适应宽度」：装不下的页面可以等比缩小（2026-09）

> 依据：用户看完 v1.39 的「装不下」横条后问「浏览器内嵌后有没有可能等比缩小，现在可视区域肯定是没有完整窗口的可视区域大的」。

**问题**：v1.39 把「装不下」说了出来，但**出口只有一个**——拖宽右栏 / 最大化窗口。
而右栏宽度上限 = 窗口内容宽 − 601（左栏 241 + 中栏下限 360），**窗口窄时这个上限本身就够不到**，
用户读完那句解释依然什么也做不了。「说出来」解决了「不知道」，没解决「办不到」。

**做法**：横条从「只解释」变成「可行动」，加一个「**适应宽度**」——把整页等比缩小到刚好装下。

- 缩放**不动原生视图的矩形**，只改页面的 CSS 视口（`setZoomFactor(z)` 把 CSS 视口变成 `区域宽 ÷ z`）。
  这是它比「把视图撑宽到 768」干净的**根本原因**：v1.20 起那条「原生视图必须与页面区域**逐像素**对齐」
  的硬约束完全不受影响（视图仍精确等于页面区域）。冒烟在缩放期间每一步都复核了这条不变量。
- 渲染层发的是**意图**（`fit: boolean`）而不是比例：比例由主进程算，因为它同时握着「区域宽」（`bounds`）
  与「页面需要多宽」（`contentWidth`）。发比例等于把这段算术复制到两个进程里。
- 比例钳在 `[MIN_FIT_ZOOM, 1]`。最窄栏（219）里装下 700px 要缩到约 31%，那已经认不出字了，
  故设**可读下限 60%**；到下限仍装不下就**如实说**（横条改写「已经缩到 60% 仍差 Npx」）
  并**撤掉那个按钮**——已经顶到下限时再按不会有任何变化，留着就是死控件（同 ⑦-F 的教训）。
- **「还原」出口常驻工具条**，不挂在横条上：一旦缩到装下，横条自己就消失了（它只在还看得见被裁时才该在），
  还原入口若跟着横条走，用户按完「适应宽度」就再也退不回去（只能刷页面）。
- **`contentWidth` 只在 `zoom === 1` 时量**。它是「页面在 100% 下需要多宽」这个**固有属性**，
  缩放会把 CSS 视口撑大，此时量出来的是缩放后的假象（看着像是本来就装得下）；拿它当输入就会
  「缩了 → 判定装得下 → 把缩放退回去 → 又装不下」来回震荡。
- `setZoomMode("isolated")`：Chromium 的缩放**默认按 origin 传播**，不隔离的话给 A 站设的比例会跟着
  origin 串到 B 站、还带上同一 partition 的其它视图。隔离后的比例**跨导航保留**，故 `did-start-navigation`
  时先把比例复位（静默复位，不推状态——随后的 `did-finish-load` 会推一份完整的）。
- 界面判「还看不看得到」必须**乘上缩放**：`contentWidth × zoom > 区域宽`。
  少了这一乘，「适应宽度」生效后页面明明已经装下、横条却仍挂在说「右边看不到」——一条立刻在撒谎的提示。

**实测（`dock` 冒烟，判据一律取页面自己的 `innerWidth`，不看界面上的百分比文字）**：
最窄栏 219 点「适应宽度」→ 页面 CSS 视口 219 → **365**（=219÷0.6，比例确实落在页面上，不是只改了个标签）；
横条改为「已缩到 60%」且按钮消失；把右栏拉到 500 → 比例**自动重算**到 71%、
页面 CSS 视口 700 = 需要宽 → 横条消失；点「还原」→ 页面回到 500 = 区域宽。
⚠️ 特别注意「比例跟着宽度重算」这一条：若比例停在上一次算出的 60% 不动，
页面 CSS 视口会是 833 而不是 700——**只有量页面才能分辨**。

**影响**：`BrowserViewState` 再加 `zoom`（**跨进程契约**）；新增 IPC `browser.zoom`（**通道数 46 → 47**，
`docs/ARCHITECTURE.md` §三有记）；`browser-host.ts` 新增 `setZoom` / `#applyFit` / `#refreshContentFit`;
渲染层 `WorkspaceDock.tsx` 横条加按钮（`data-browser-fit`）、工具条加缩放指示与还原（`data-browser-zoom` /
`data-browser-zoom-reset`）。**缩放期间原生视图的逐像素对齐不受影响**（本次未动 `setBounds`）。
夹具站未改动（复用 `/narrow.html`：它在最窄栏装不下、在 500 宽栏刚好缩得动）。

验收：`typecheck` / `build` / 单测 **557**（未动）/ `fixture` **25/25**（未动）/
`dock` **189/189**（177 → 189，新增 12 条：出口可点 2 + 页面真的缩了 2 + 顶到下限如实说 2 +
缩放期间仍逐像素对齐 2 + 宽栏重算 2 + 还原 2）。

### v1.42 —— `/skill` 斜杠命令：把「按名调用技能」变成用户够得着的能力（2026-09）

> 依据：修掉「模型看不见技能清单」的静默失败之后，`resources.skills` 那半仍然**没有任何入口**——
> `disable-model-invocation: true` 的技能能装进来、能在通知里列出来，却**没人调得动**
> （当时通知里那句「等于不生效」是事实陈述，不是吓唬人）。

**问题**：技能有两条互不相干的通道（见 `ARCHITECTURE.md` §四）：模型**看见清单**靠应用拼系统提示词，
**按名调用**靠 `resources.skills`。前者已接，后者只在内核里存在——没有命令、没有按钮、没有 IPC。

**做法**：输入框加第二条斜杠命令 `/skill <技能名> [额外指示]`。三条刻意从紧的规则：

- **零参数命令与带参数命令分开判**：`/compact` 仍要求**独占整条输入**（多一个字符都不算命令）；
  `/skill` 则**必须给名字**——只写 `/skill` 不算命令，回落成普通提问（防误吞，同 v1.34 的纪律）。
- **未知技能名不回落**：报一条**可见错误并列出可用技能名**（v1.43 起这次判定**前移到渲染层**，
  见下条与 v1.43 条目）。这是对「整串相等、未知一律放行」的一次**有意偏离**：那条纪律防的是
  **静默**吞掉用户输入，而技能名是用户自己在磁盘上定的，打错时最需要的恰恰是「正确写法是什么」。
  ⚠️ 本版仍**先清空输入再发**，于是名字后那半句额外指示会跟着一起没掉——**v1.43 修掉了这一点**。
- **运行中不转成 `steer`**（与 `promptOrReconnect` 不同）：把一句话当插话送进去是自洽的，
  但把一次技能调用偷偷降级成一句话会改变语义（用户以为调了技能，实际只是说了句话）；
  改由内核返回 `LaneBusy` → 可见报错。
- **不做按钮 / 菜单**：技能清单渲染层拿不到（**本版** `ConversationView` 无此字段——v1.43 补上了
  `skills`，那条限制随之解除），而输入工具行已经有 4 个控件（那一行还有溢出回归由冒烟守着，见 `smoke.ts`）。
  可发现性改由**会话启动通知**承担：列出技能名（最多 8 个）+ 写明 `/skill <名字> 调用`。

**影响**：新增 IPC `session.skill`（**通道数 47 → 48**，`docs/ARCHITECTURE.md` §三有记，
`ChannelParityChecked` 的编译期断言会拦住漏登记）；`shared/worker-protocol.ts` 的 `WorkerCommand`
加 `skill`；`worker/entry.ts` 加 `case "skill"`（**先在本进程自查名字**，再交给内核，
并**检查 `Result.err`**——内核的技能失败走返回值而不是抛异常，不查就是「敲了没反应」）；
新增 `worker/lib/skill-error.ts`（报错文案，**有单测**；v1.43 移到了 `shared/skill-error.ts`，
好让渲染层与 worker 说**同一句话**）；`renderer/src/lib/slash-command.ts`

### v1.43 —— 打错技能名时**不再吃掉那半句额外指示**：技能清单成为渲染层的数据（2026-09）

> 依据：v1.42 之后 `/skill` 能用，但**打错一个字母就要重打整句**——用户实测报的就是这个现象
> （名字后面那半句指示跟着输入一起没了）。

**问题**：`invoke("session.skill")` 只返回「**已投递**」，worker 的校验收在 `session.error`
**推送**里——提交那一刻渲染层判不了成败。而 v1.42 的写法是**先清空再发**：等错误回来，
用户敲的那句话已经没了。**判据不在渲染层手里，就只能在事后补救。**

**做法**：把「这个名字存不存在」的判定权交给**渲染层**——它是唯一能在提交当刻做决定的一方。

- **给 `ConversationView` 加 `skills: string[]`**（跨进程契约）：worker 装载技能时把**名字**一并投影
  出来（装载后固定，会话内不变）。正文与内核侧的清单照旧在 worker，这里只多一份**只读名单**。
- **渲染层本地拦下**（`lib/slash-command.ts` 的新纯函数 `resolveSkillCommand`）：名字不在名单里
  → **不清空输入**、报一条可见错误，用户改一个字母就能重敲。
- **worker 那条降级为兜底**：渲染层拿不到清单时（没有 worker / 还没上报）从宽放行，由 worker 报错。
  但**文案两边共用同一份**（模块移到 `shared/skill-error.ts`）——同一个错误不该因入口不同给出两种说法。

**⚠️ 本条的判据全在 `undefined` 与 `[]` 的区别上**：拿不到视图时 `view?.skills` 是 `undefined`
＝**不知道**；`[]` 才是**知道，且一个技能都没装**。只有后者能安全拒绝——凭「不知道」拒绝会把一次
**有效**调用误判成失败，那是**另一种**丢输入（且用户看不懂：「明明有这个技能文件」）。
所以三种取值必须区别对待，单测**专门断言 `resolveSkillCommand("pdf", undefined)` 与 `("pdf", [])` 不相等**。

**影响**：`ConversationView` 新增 `skills`（**跨进程契约变更**）；`worker/entry.ts` 把技能清单从
`WorkerState` 顶层挪进 `meta` 再投影进视图；**新建** `shared/skill-error.ts`（从
`worker/lib/skill-error.ts` 移入，**worker 与渲染层共用同一份文案**）；`lib/slash-command.ts` 加
`resolveSkillCommand`；`Conversation/index.tsx` 的 `submit` 在 `/skill` 分支里**先判后清**。

**副产品**：v1.42 那条「不做技能选择器 / 菜单」的限制（理由是渲染层没有清单）**随之解除**——
清单现在就在渲染层手里。选择器本身仍未做：输入工具行 4 个控件的溢出约束没变。

**陪跑修掉的一处冒烟夹具缺陷**（单独记，因为它的症状**长得像产品坏了**）：`smoke.ts` 的
`smokeView()` 造的受控视图会经 `session.view` **整份替换**渲染层那份真实视图，而它的类型当时是
`Record<string, unknown>`——**少写字段编译器不管**。本版给契约加了 `skills`，夹具没跟上，
于是渲染层把清单读成 `undefined`、本地拦截**整条失效**：4 条新断言全红，报的却是「拦不住」。
把基准对象的类型钉成 `ConversationView`（覆盖项用 `Partial<ConversationView>`）后立刻转绿——
**以后契约再加字段，这里会编译不过，而不是静默抹成 `undefined`**。详见 `AGENTS.md` ⑪。

验收：`typecheck` / `build` / 单测 **589**（584 → 589，新增 5 条：`resolveSkillCommand` 的四条分支
——含「`undefined` ≠ `[]`」与「精确匹配、大小写敏感」）/ `fixture` **25/25**（未动）/
`dock` **195/195**（193 → 195，本段由 4 条改成 6 条：新增**前置**「夹具视图带清单」1 条与
「拦下时输入原样留着」1 条，并把原先拆成两条的「走技能通道 / 不发普通提问」并成一条
**「既不走技能 IPC、也不变成普通提问」**）。
⚠️ 仍沿用 v1.41 的规矩：`dock` **只记账、不转发**；夹具里 `skills` 取 `[]`
（＝知道且为空），正是本地拦截该生效的那种情形。

### v1.44 —— `/` 候选浮层：让技能**不必记住名字**也能调用（2026-09）

> 依据：v1.42 起 `/skill <名字>` 能用，但**名字只能靠自己记**——唯一的告知渠道是会话启动通知里那
> 一行「已加载 N 个技能：a、b、c……用 /skill <名字> 调用」，最多列 8 个，消息一多就翻过去了。
> 而技能名是用户自己在磁盘上定的，记不住就等于调不动。

**问题**：技能的可发现性一直挂在**一行通知**上。v1.43 已把技能清单（`ConversationView.skills`）送到
渲染层，前置具备了；剩下的抉择是**这个入口做成什么形态**。

**为什么不做成工具行按钮**：工具行（`.comp-tools`）已有 4 个控件、是 `flex-wrap` 的，且背着一条
真实回归——「一个可用模型都没有时（主区顶部多一条黄条），输入卡片与工具行必须**完整落在窗口内**，
不能被 `main` 的 `overflow-hidden` 从底部裁掉」。再挂一个常驻控件就是把这个空间问题推给那条回归
（见规则 ⑤-C / ⑤-E）。

**做法**：**敲 `/` 弹候选浮层**（`lib/slash-command.ts` 的新纯函数 `slashCandidates`），
`absolute bottom-full` 向上弹——**不占任何布局**。

- 候选 = `/compact` + 本会话每个技能各一项；选中即把命令**写回输入框**（技能项带**尾随空格**，
  好接着写那半句额外指示），并把光标落在末尾。
- 匹配只有一条规则，但它的**后半句是命门**：候选文本以当前输入为**前缀**，且**不等于它自己**。
  少了后半句，用户把 `/compact` 敲全之后浮层仍然开着，那一下回车会被「选中」吃掉——
  **敲对了命令反而发不出去，得先按 Esc**。加上它，敲完整条命令浮层自己让开。
- 同一条规则顺带覆盖三种边界，没写任何特例：裸 `/` 全列；`/usr/local/bin` 这类路径**一个都匹配不上**
  （浮层不出现，照常当正文发出去）；`/compact 一下` 也匹配不上（前缀比候选长）。
- **Enter 的双重语义是本条最大的风险点**：浮层开着时 Enter / Tab 是「**选中**」，关着时仍是「发送」。
  不显式拦这一下，用户选技能的那次回车会把半截命令（`/skill pd`）当正文发出去——技能没调用、
  输入还没了。`Esc` 则**只收浮层、不动输入**（清空输入是 N2 里还没定的另一件事，不能顺手替用户决定）。

**影响**：`lib/slash-command.ts` 加 `slashCandidates` + `SlashCandidate`（**有单测 10 条**）；
`Conversation/index.tsx` 给 `textarea` **套了一层 `relative` 容器**（浮层靠它定位）、加了浮层 JSX
与三段键盘规则、给输入卡片加了 `data-conv-card` 标记；**输入卡片本身的结构与高度不变**。

⚠️ **陪跑修掉一处探针的「静默变松」**（症状是 2 条附件断言变红 + 1 条断言悄悄失效）：
原有两个探针把「`textarea.parentElement`」当成**输入卡片**——套上那层容器之后，`parentElement`
变成了那层容器，于是 `card.querySelector("[data-conv-attach-notice]")` 再也找不到提示（那 2 条红），
而 `model/no-usable` 的「输入卡片完整落在窗口内」则改为去量一层**恒在卡片内**的容器——
**断言从此变松，且看不出任何异常**。两处都改成按 `[data-conv-card]` 认。
铁律：**探针别靠层级猜元素**，给被测结构一个它自己的标记（同 `[data-conv-error]` / `data-dock-tab`）。
