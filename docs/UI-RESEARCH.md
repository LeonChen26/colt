# Colt 界面设计 · 调研报告

> 作者：Colt
> 目的：在出设计稿之前，先弄清楚**这个领域已经形成了什么共识、头部产品踩过什么坑、工业标准如何建模**。
> 方法：GitHub API 一手检索同类产品（星标 / issue 原文 / README）+ 研读 ACP（Agent Client Protocol）官方 JSON Schema。
> 日期：基于仓库检索当日的公开数据。

---

## 0. 为什么要先调研

前两版设计稿的毛病是**自嗨**：坐在屋子里推演"用户应该这样"，而非"用户实际这样"。
本报告用三类**一手证据**纠偏：

1. **同类产品的功能清单**（他们在做什么）
2. **真实用户的 issue 原文**（他们被什么惹恼）
3. **ACP 协议的交互模型**（工业标准怎么定义）

---

## 1. 同类产品格局

### 1.1 头部产品一览（GitHub 星标）

| 项目 | ★ | 技术栈 | 一句话 |
|---|---|---|---|
| **cc-haha** | 14.3k | Electron + TS | Claude Code 桌面工作台，功能最全 |
| **opcode** | 22.4k | Tauri + Rust | Claude Code 的 GUI 与工具箱 |
| **claudecodeui** | 13.7k | React | 多 CLI 的 Web/移动 UI |
| **codeg** | 3.4k | Rust | 多 agent 协作工作台（聚合 CC/Codex/OpenCode/Pi） |
| **PI-Desktop** | 2.9k | Electron + Rust | 本地优先编码 agent 桌面端 |

**关键观察**：
- 这个赛道**极其拥挤且高度同质化**。几乎全部产品都在做同一件事：**把 CLI agent 包上一层 GUI**。
- 头部产品的功能高度趋同：多会话、diff 审阅、权限审批、模型自选、MCP 管理、用量统计。
- **"做出来"不等于"做好用"**——22k 星的 opcode 和 14k 星的 cc-haha，issue 区依然充斥着基础体验问题。

> 对我们的意义：**功能堆砌没有护城河，交互质量才是**。Colt 不应追求功能数量，而应在"一个核心交互做到极致"。

### 1.2 头部产品的功能构成（cc-haha 为例）

其 README 罗列的能力：多会话与全局搜索、分支/Worktree、Diff 审阅、内置浏览器预览、图形化权限审批、模型自选、图片生成、MCP 与 SubAgent 可视化、Agent Teams 协作、Workflow 编排、请求追踪、Computer Use、技能市场、多主题、桌面宠物、远程访问、IM 接入、定时任务。

**观察**：这是典型的"功能膨胀"。**桌面宠物、IM 接入、技能市场**这些与"编码"核心任务关系很弱。功能越多，核心路径越容易被淹没。

## 2. 真实用户的痛点（最关键的证据）

从 cc-haha (#1239 等) 与 codeg (#709 等) 的 issue 原文中提炼。**这些是坐着想不出来的**。

### 痛点 A：**"卡住"是头号杀手**
> "[问题] 卡在一个步骤十几分钟了"
> "[BUG] 有些任务或者有些模型的时候遇到权限问题直接卡住不回复"
> "程序一打开就一直在 loading 中"
> "hermes agent 完成任务之后一直没有终止"

**问题本质**：用户无法区分「Agent 在思考」和「Agent 挂了」。
**设计启示**：
- **必须有"心跳"**：任何等待状态都要有可见的运动（计时器、心跳、最后活跃时间）。
- **必须能打断**：卡住时一键中断，且中断后状态要干净。
- **必须能解释**：卡在授权、卡在 API、卡在思考，要能区分并明说。

### 痛点 B：**错误信息驴唇不对马嘴**
> "#1239 超过上下文窗口后，请求被错误提示为'模型不存在或无权限'"

原文非常典型：真正原因是**上下文超限**，但界面显示**"模型不存在或无权限"**，把用户引向完全错误的排查方向。

**设计启示**：
- **错误信息是第一等公民**，必须显示**真实原因 + 建议动作**，不能透传底层原始报错。
- 上下文超限这种**可预判**的情况，应该在**发生前**就预警（进度条 + 一键压缩），而非事后报错。

### 痛点 C：**状态更新不及时 / 不一致**
> "后台任务有时候状态不更新及时"
> "codeg #709: Auto-approve tools 开关无法切换状态"（点了没反应）

**设计启示**：
- **状态必须实时、且可见地同步**。乐观更新 + 服务端确认的实际反馈。
- 切换类控件必须**立即给出视觉反馈**，哪怕后端还没返回。

### 痛点 D：**权限/审批流程会"卡死"整个流程**
> "遇到权限问题直接卡住不回复"

**设计启示**：这与 ACP 标准不谋而合（见 §3）——授权请求必须有**超时机制**、**明确的取消语义**、**不能静默消失**。Colt 现有实现已有 5 分钟超时（`APPROVAL_TIMEOUT_MS`），但**界面上没体现出来**。

### 痛点 E：**信息架构混乱**
> "文件管理看起来有点乱，不够清晰。预期是查看某个文件夹下的所有内容，但展示不到 2 秒就切换成 d 盘"

**设计启示**：**自动行为不能抢用户的注意力**。用户正在看的视图不能被后台事件顶掉。

### 痛点 F：**流式输出不可控**
> "可以增加关闭流式输出吗？免费额度用户不想被时代放弃"

**设计启示**：**性能与成本敏感的用户需要控制权**。流式、动画、轮询都应有"省流"开关。

## 3. ACP 协议：工业标准如何建模（核心发现）

**Agent Client Protocol**（4.2k★，Zed 主导）= 标准化"编辑器 ↔ 编码 agent"的通信。schema 170 个类型定义，是**这个领域正在收敛的事实标准**。

### 3.1 它的实时更新模型（SessionUpdate · 11 种）

这是**界面应该支持的全部实时状态**——直接给出了一份界面设计的检查清单：

| 更新类型 | 含义 | 界面应对 |
|---|---|---|
| `user_message_chunk` | 用户消息流式 | 输入回显 |
| `agent_message_chunk` | Agent 回复流式 | 正文流式 |
| **`agent_thought_chunk`** | **Agent 内部推理流式** | **独立的"思考"展示区** ⭐ |
| `tool_call` | 新工具调用发起 | 工具卡片创建 |
| `tool_call_update` | 工具调用状态/结果更新 | 卡片状态刷新 |
| **`plan`** | **执行计划** | **计划面板** ⭐ |
| `available_commands_update` | 可用命令变化 | 命令菜单 |
| `current_mode_update` | 会话模式变化 | 模式指示器 |
| `config_option_update` | 会话配置变化 | 配置面板 |
| `session_info_update` | 会话元数据变化 | 标题更新 |
| **`usage_update`** | **上下文窗口 + 成本** | **用量条** ⭐ |

**我们之前漏掉的关键项**：
- **`agent_thought_chunk`**：把"思考"作为**独立一等类型**。这解决痛点 A（"不知道它在干嘛"）——用户的安心感来自看到它的思考流。
- **`usage_update`**：标准明确包含 `used` / `size`（上下文窗口占用量）+ `cost`。**上下文是持续更新的状态，不是事后统计**。
- **`available_commands_update`**：命令是**动态下发**的，界面应有个随 agent 变化的命令菜单。

### 3.2 工具调用模型（ToolCall）

```
ToolCall {
  toolCallId, title,           // 一键标识 + 人类可读标题
  kind,                        // read|edit|delete|move|...（决定图标与展示方式）
  status,                      // pending | in_progress | completed | failed
  content[],                   // 输出：文本/图片/**Diff**
  locations[],                 // ★ 正在访问/修改的文件位置
  rawInput, rawOutput
}
```

**三个关键设计点**：
1. **`kind`** 枚举 → 界面据此选图标、"优化进度展示方式"。**工具应有类型语义，不只是名字**。
2. **`content` 里含 `Diff`** → diff 是**工具内容的一等类型**，不是事后附加。工具卡片可直接内嵌 diff。
3. **`locations`** → ACP 明确说这支持 **"follow-along"（跟随）特性**："实时追踪 agent 正在处理哪些文件"。⭐ **这是我一直没设计的**：一个跟随 agent 当前工作文件的视图。

### 3.3 授权模型（Permission）

```
RequestPermissionRequest { sessionId, toolCall, options[] }
PermissionOption { optionId, name, kind }
  kind: allow_once | allow_always | reject_once | reject_always
Response: SelectedPermissionOutcome(optionId) | Cancelled
```

**决定性发现**：
- 授权选项是 **agent 提供的**（`options[]`），不是客户端写死的。界面应**渲染 agent 给的选项**，而非硬编码"允许/拒绝"。
- 标准就是四档：**允许一次 / 永远允许 / 拒绝一次 / 永远拒绝**。这与我在 v2 提的"就地授权"方向一致，但**粒度定义更清晰**。
- **`Cancelled` 是明确的一等结果**：取消 prompt turn 时，所有待决授权必须以 Cancelled 结束。解决痛点 D（授权卡死）。

### 3.4 计划模型（Plan）

```
Plan { entries[] }
PlanEntry { content, priority(high|medium|low), status(pending|in_progress|completed) }
```
- 计划是**结构化条目**，每项有**优先级**和**状态**。这印证了 v2 的 Plan 方向，且补充了**优先级**维度。

### 3.5 会话模式（SessionMode / SessionModeState）

```
SessionMode { id, name, description }
SessionModeState { currentModeId, availableModes[] }
```
- **模式是 agent 定义、可动态变更的**（`current_mode_update`），不是客户端写死的全局开关。
- 这直接**证伪了我 v1 的"全局审批模式徽章"**——模式应该是**会话级、agent 可主动切换**的。

## 4. 结论：对设计的六条纠正

| # | 调研发现 | 对设计的纠正 |
|---|---|---|
| 1 | "卡住"是头号投诉 | 一切等待态必须有**心跳/计时器**；授权要**可见超时**；中断要**状态干净** |
| 2 | 错误信息误导用户 | 错误须为**真实原因 + 建议动作**；可预判问题（上下文超限）要**事前预警** |
| 3 | 思考流是独立类型 | **新增"思考"展示区**，把 agent 内心活动可视化（治"不知道在干嘛"） |
| 4 | 上下文/成本是持续状态 | 用量是**实时状态条**（used/size/cost），非事后统计页 |
| 5 | 授权选项由 agent 提供 | **渲染 agent 给的选项**，支持四档语义 + Cancelled；不要硬编码 |
| 6 | locations 支持 follow-along | **新增"文件跟随"视图**：实时显示 agent 正在碰的文件 |

**还有一条元结论**：功能堆砌没有护城河（见 §1）。Colt 的差异化不应是"我也有多少功能"，而应是**把"可观测性 + 可控性"这一对核心体验做到最好**——正好对应用户最痛的两件事：**不知道它在干嘛**（可观测）+ **卡住停不下来**（可控）。

---

## 5. 下一步

基于本报告重做设计稿（v3），核心变化：
- 主轴从"任务"进一步落实为 **"会话现场（Live Session）"**——一个以**实时可观测**为第一优先的界面。
- 新增三个调研得来的关键模块：**思考流**、**文件跟随**、**实时用量条**。
- 重做**授权卡**以对齐 ACP 四档语义 + 超时可取消。
- 全套**心跳与中断**机制。
