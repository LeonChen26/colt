## 2. 已定调，不要重新讨论

- ⑦ 是**工作区容器**，不是浏览器专用栏；以页签切换视图，「正在处理」是默认视图且**不可关闭**（可折叠）
- 浏览器载体是 `WebContentsView`，**不回退到独立窗口**；页面用**独立 partition**
- 视图**懒创建**：未激活的页签不创建 WebContents
- ⑥ 是**只读区**，不放任何操作（中断属于 ⑤）
- ⑥ 的位置在输入区**下方**
- **⑦ 的宽度是全局统一值 544**（v1.24）——**不按页签取建议值**。理由：按视图各给一个宽度会让切页签就改宽度、
  中栏跟着反复重排。**别再引入「每个视图一个建议宽度」**（原型的 `VIEW_RATIO` 就是这么画的，是刻意不采纳的）
- **⑥ 的非运行态是四态**（v1.25）：运行中 / 已中断 / 已失败（带 error 摘要）/ 空闲；
  **正常跑完回「空闲」**，不为一次正常结束留痕；状态是**电平**（留到下一轮跑完）
- 会话语义模式选择器（原违规 #8）**暂不处理**
- ③ 的 L1（模式切换）/ L2（功能入口）分层：功能尚未落地，规则**暂无适用对象**

### 已订正的事实（曾经写反过，别再照着做）

| 曾经的结论 | 真相 | 出处 |
|---|---|---|
| 「用户自己无法操作内嵌浏览器，缺的是按钮」 | **错**：那是个真实 `WebContentsView`，用户本来就能直接点它；缺的只是后退/前进/刷新按钮 | v1.19 |
| 「跟随线（follow line）可以收成右侧边缘标签 / 浮层」 | **过期**：跟随线在本产品里已不存在，它成了 ⑦ 的默认页签「正在处理」（`FollowPanel.tsx`）。v3 §8 的四档是按旧模型写的 | v1.23 / 本文档 §3.1 N3 |
| 「bing 首页自己不会横向溢出」 | **错在判据**：`documentElement.scrollWidth` 被页面自带的 `overflow-x: hidden` 钳到 `clientWidth`，是**必然为真的假阴性**。实测 `div.hp_body` 有 768px 最小内容宽，停靠区 <783 就真溢出（且没有横向滚动条，裁掉的部分用户够不到） | v1.21 → v1.23 |
| 「`faulted` 可以表达任务的异常结束」 | **错**：它是 harness `fault` 事件的**会话级硬故障**标记，内核**从不复位**它。轮次终态要看 `lastResult.status` | v1.25 |
| 「渲染层传下来的 `cwd` 就是读文件的根」 | **错**：根只在 `projects.root_path` 上（`sessions` 表不存 cwd），必须由主进程按 `sessionId` 查 DB 推出 | v1.13 |
| 「`file.read` 只收相对路径」 | **站不住**：工具入参里的 path 由模型给出，实测常是绝对路径；安全靠**越界校验**（先于任何 fs 访问），不靠限制写法 | v1.14 |
| 「浏览器该做成独立窗口，便于用户旁观与授权」 | **旧前提**，被 ⑦-C 推翻：内嵌恰恰更利于旁观。这是「把现状当约束」的典型（`AGENTS.md` §3.1） | v1.8 → 内嵌 |

#### N1 观测抽屉的「条目详情」（原型有、产品只有列表）

- **依据**：原型 `.observe` 的网络页签画的是**单个失败请求的详情**（401 + 时间戳）；
  产品只做了平铺列表（一行一条 + 计数徽标）
- **现状**（`ObserveDrawer.tsx` 实测）：
  - console：`message` 会 `break-words` 完整显示，但**来源被 `shortSource` 压成文件名**，完整 `source` 看不到
  - network：整行 `truncate`，完整 URL **只能在原生 tooltip 里看**（`title`）
  - downloads：`path` 也 `truncate`（`title` 兜底）
  - 三份数据都**没有**时间戳 / 耗时 / 请求头字段
- **范围（分两半，别混成一件）**：
  - **纯前端可做（建议先交付这一半）**：点一行展开——console 给完整 `source:line` + 完整 message；
    network 给完整 URL / `method` / `resourceType` / `statusCode` / `error`；downloads 给绝对 `path` / `bytes` / `state` / `note`。
    顺带一个**复制**按钮：`navigator.clipboard.writeText` 在本仓已有先例（`App.tsx` 复制会话 ID、`Markdown.tsx` 复制代码），**不需要新 IPC**
  - **要扩主进程的那半**：**时间戳 / 耗时 / 请求头**——`ConsoleEntry` / `NetworkEntry` 当前都没有。
    要不要加先定；注意 `CaptureBuffer` 是唯一写入方，加字段会牵动 `browser_read` 给模型的文本
    （`formatConsole` / `formatNetwork`），**别顺手改那段**（它被压缩过是刻意的）
- **依赖**：无（先做纯前端那半完全不碰主进程）
- **验收**：单测（详情行的字段映射是纯函数）+ `dock` 冒烟（点条目 → 断言详情内容出现；**长文本不被截断**的判据）
- **为什么排第一**：最小、纯前端，补的却是 ⑦-A「现场」里最高频的一问——「刚才那个 401 是什么」

#### N2 全局快捷键（v3 §7）的一个子集

- **依据**：v3 §7 快捷键表；原型 `.dock-head` / `.nav-btns`（B1 已把按钮做上，键盘还没有）
- **现状（实测）**：渲染层**全仓只有两处键盘处理**——⑤ 输入框的 `Enter`（发送 / 插话）、
  右栏「+」菜单的 `Esc`（收菜单）。`⌘.` / `Esc` 中断、`⌘N` 新会话、`⌘⏎` 提交授权**都没有键盘入口**
  （`abort()`、`App.tsx` 的 `newSession()` 函数都在，只是没接线）
- **范围**：`Esc` / `⌘.` 中断；`⌘N` 新会话；`⌘⏎` 提交授权
- **动手前必须先定的两件事**：
  1. **`⌘⏎` 批准哪一张卡**：审批是**列表渲染**（`approvals.map`），同时可能有多张待批。
     规则要显式写出来（「批准最早一张」？「只批准有焦点的那张」？），且键盘路径要有**可见反馈**——
     否则用户不知道刚才那一下批了什么
  2. **`Esc` 与输入框的关系**：在 textarea 里按 Esc 是中断，还是先清空/收起输入？v3 写的是 `⌘.` / `Esc` 都中断
- **明确不做 `⌘I` / `⌘L`**：目标**不存在**——思考轨是**自动折叠**的组件（`MessageList.tsx` 的
  `ThinkingRail`：运行中折叠成一行标题），「跟随线」在本产品里是 ⑦ 的默认页签「正在处理」，
  不是一条可折叠的线。做了就是两个**死快捷键**（`AGENTS.md` §3.6）。
  **要么从 v3 §7 表里划掉，要么先设计一个「折叠正在处理里的某一段」**——不要直接做成空绑定
- **验收**：单测（「按键 + 当前上下文 → 意图」是纯函数，含「焦点在输入框内」的例外）+ `dock` 冒烟
  （真派发键盘事件 → 断言中断 IPC 真的发出 / 新会话真的被创建）

#### N3 响应式四档 —— v3 §8 的模型**已过期，不能照抄**（先出设计）

- **依据**：v3 §8（≥1360 三栏 / 1100–1360 右侧边缘标签 / 900–1100 浮层 + 左栏图标条 / <900 单栏）
- ⚠️ **v3 §8 是按旧的「跟随线」模型写的**：它假设有一条可以收成「右侧边缘标签 / 浮层」的**跟随线**。
  产品里**跟随线已不存在**——它成了 ⑦ 的默认页签「正在处理」。所以四档必须**从当前三栏现实重推**：
  ③ 左栏 / 中栏（②④⑤⑥）/ ⑦ 右栏。**照抄 v3 §8 会设计出一个不存在的组件**
- **硬约束（实测）**：
  - 三栏同时拿到各自下限需要窗口 ≈ **836**：左栏 `w-[240px]` + 1px 边框、中栏下限 360、右栏下限 220，
    加上约 15px 内边距（窗口 1440 时三栏可用宽实测 **1184**；右栏上限 = 可用宽 − 360）
  - 窗口再窄时**右栏被钳在 220 不再让位，而中栏会继续被压**——grid 是 `minmax(0, 1fr)`
    （`index.tsx:646`），**中栏没有硬兜底**，能被压到几乎不可用。**这是本项真正的痛点**
  - **⑦ 是原生视图**：任何布局级折叠都必须**同步 `browser.bounds`**，否则视图会浮在错位置。
    ⚠️ 这属于 `AGENTS.md` §5 第 ⑤ 条那类「电平状态别用边沿事件同步」的问题
  - ⑦-E「可折叠、不提供完全关闭」与「折叠时收起原生视图」的既有语义要沿用
- **要定的**：每一档**丢什么**（左栏→图标条？右栏→自动折叠？中栏能压到多窄？）、切换**可不可逆**（窗口回大是否自动恢复）、
  窗口窄于三栏下限时的行为（单栏 + 顶部页签切换？）
- ⚠️ **原型不覆盖这一块**（它是固定宽度的概念稿）→ 本项**必须先补设计**，或明确「不做，窗口过窄时不支持」
- **顺手处理**：`styles.css` 的 `--w-sidebar: 248px` **声明了但全仓无人引用**（左栏实际是 `App.tsx:295` 的
  `w-[240px]`）——设计这一档时把它用起来或删掉
- **验收**：`dock` 冒烟扩到多档（每档断言：中栏没被压破、**原生视图与页面区域仍然逐像素相等**、折叠可逆）

#### N4 停靠 / 弹出双态（B3）—— 原型方案与 ⑦-C 直接冲突（先出设计）

- **依据**：原型 `.dock-head` 的两个按钮（`停靠在窗口内` / `弹出为独立窗口`），原型正文也写明
  「双态切换：需要大屏时用户自己弹出去，形态权交给用户」
- ⚠️ **不能照抄**：直译「弹出」就是回到**独立窗口**，而 ⑦-C「视野跳跃必须为零」存在的理由就是消灭那个外部窗口
  （历史上 `browser-host.ts` 的注释写着「便于用户旁观与授权」，那是**旧前提**，见 §2「已订正的事实」）
- **可选方向（三选一，先选再设计）**：
  - **(a) 全屏查看**：仍在**同一个窗口、同一个 `WebContentsView`**，只是把矩形放大到整窗
  - **(b) 放大到「中栏 + 右栏」**：保留左栏，退出路径更显眼
  - **(c) 不做**，并记进「已否决」——同时把原型那一行标成「不实现」（免得下一个人又来问）
- **可行性（已读代码）**：主进程 `#applyBounds` 的摆放是「**渲染层上报的矩形** + 可选 `viewport` 覆盖」——
  渲染层报一个更大的矩形就能放大，**不需要新增主进程机制**
- ⚠️ **设计时必须留出退出入口**：原生视图浮在渲染层**之上**，全屏后会把渲染层画的「退出」按钮一起盖住。
  要么给视图让出一条带（例如保留 ⑦ 头部 / 一行工具条），要么退出只走键盘——**那就得先把 N2 做掉**。
  「进得去出不来」是死控件的新变种（`AGENTS.md` §3.6）
- **不要复用旧 `BrowserWindow` 方案**（销毁路径判活那批坑）
- **验收**：`dock` 冒烟（放大后原生视图矩形 == 放大区域；退出按钮**命中测试**通过——`elementFromPoint`，
  不能只看「在 DOM 里」）

（用户报「浏览内容溢出、显示不全：①侵占下方控制台 ②右边显示不全」，查下来是**两个独立缺陷**）

- **缺陷一：原生视图的矩形是「电平」状态，同步却是「边沿」触发。**
  视图必须**一直**等于渲染层的「页面区域」，而 `ResizeObserver` / `window resize` 都是边沿触发——
  **漏一次边沿，它就永久错位**。实测抓到过一次：页面区域 591 高、原生视图停在 723（正好是抽屉收起时的高度，
  多出的 132px = 抽屉正文高度），于是压住观测抽屉。
  - 之所以长期没被发现：冒烟只验过「收起/展开时高度**会变**」，**从没验过「与区域相等」**。
  - 修：边沿触发之外，浏览器页签可见时每 400ms 重申一次矩形（电平状态就该这样收敛）；
    并补上不变量断言——视图须与页面区域**逐像素**对齐，且反复收起/展开 **5 轮**都成立。
- **缺陷二：`browser_act viewport` 留下的覆盖是「隐形」的。**
  `#applyBounds` 里 `size = entry.viewport ?? 实际布局`：覆盖优先且**只在显式「恢复」时才撤销**。
  实测（停靠区 823×643）：覆盖 1280×800 → 视图右边到 1881、而窗口内容右边只有 1672（**209px 被窗口裁掉**），
  下边到 907、而区域下边只有 750（**157px 压住观测抽屉**）——**界面上完全看不出这是联调尺寸**，
  用户只会以为渲染坏了。（顺带订正：`#applyBounds` 原注释写「渲染层一旦重新上报，覆盖即让位于真实布局」，

    一眼看出是「联调留白」而非没渲染出来。

  `zoomFactor` / `devicePixelRatio`，三个结论：
  1. **页面视口精确跟随原生视图尺寸**：视图 823 → `innerWidth` 823，视图 400 → 400，视图 1200 → 1200，
     `zoomFactor` 与 `dpr` 恒为 1。先前一度读到「视图 823 而 `innerWidth` 543」，是那一轮右栏恰好是 543 宽，
     不是失真——**读数异常时先确认"当时那个量本身是多少"，别急着当成 bug**。
  2. ⚠️ **先前那条「bing 首页自己不会横向溢出」是错的，在此订正。** 错在判据：
     `documentElement.scrollWidth` 会被页面自己的 `overflow-x: hidden` **钳到 `clientWidth`**，
     于是不管页面装不装得下，它都「等于」`clientWidth`——**一个必然为真的假阴性**。

     `getBoundingClientRect().right` 的最大值），真实情况是：bing 首页的 `div.hp_body` 有

     | 停靠区（区域）宽 | 页面 `body.scrollWidth` | 最右元素 | 结论 |
     |---|---|---|---|
     | 819 | 804 | 807 | 装得下 |
     | 799 | 784 | 797 | 装得下 |
     | 779 | 768 | 787 | 溢出 4px |
     | 759 | 768 | 777 | 溢出 24px |
     | 739 | 768 | 768 `DIV.hp_body` | 溢出 44px |
     | 699 | 768 | 768 `DIV.hp_body` | 溢出 84px |

     所以「右边显示不全」在**窄右栏**下是一条真实来源，不是「只能是覆盖」。

  3. 「超出」在**宽右栏**下只剩**视口覆盖**：`size = entry.viewport ?? 实际布局` 让原生视图比停靠区大，

     **一次同时给出用户报的两个症状**（这正是它区别于缺陷一的地方：缺陷一只有「压住下方」）。
     用户第二张截图（右栏 1045 宽、Bing 仍右侧被裁）正是这一条：1045 > 783，页面本该装得下，
     唯一的解释就是此刻**有一个 1280 量级的覆盖在生效**——他跑的是**加标记之前的构建**，
     所以既被裁、又看不到那个「联调视口 × 恢复」标记。

## 7. 上一阶段踩过的坑（下一阶段别重踩）

- **原生视图不参与 DOM 叠层**：`WebContentsView` 浮在渲染层之上，切走页签 / 卸载会话时**必须上报隐藏**，否则会盖住别的内容
- **销毁路径必须判活**：`webContents` 一旦 destroyed，访问任何属性都会抛；顺序是「摘出视图 → 判活 → 关」
- **`capturePage` 拍不到原生视图**：验证内嵌浏览器必须用**系统级截图**，主窗口 `capturePage` 里不会出现它
- **容器查询要设在「中栏宽度」上**，而不是窗口宽度（`max-w-[796px]` 把内边距包进容器才对得上）
- **`viewport` 语义已变**：不再改窗口尺寸，而是给视图覆盖尺寸
- **渲染层传下来的 `cwd` 不能直接当「读文件的根」**：`cwd` 由渲染层交给主进程（`Conversation` 的 prop）。
  读文件能力必须由**主进程按 `sessionId` 查 DB 取根**，渲染层给的路径**必须落在根内**
  （相对/绝对皆可——工具入参里的 path 由模型给出，可能是绝对路径；关键是**越界判断先于任何 fs 访问**，
  这样根外路径不会变成「存在性探测」的口子）。
  **已按此落地**（A3-2，`src/main/file-read.ts`）；另更正两处事实：
  ① 根**不在 `sessions` 表**（它不存 cwd），只在 `projects.root_path` 上；
  ② 原「只收相对路径」在实测中站不住——`read` 既不产生改动记录、入参又可能是绝对路径
- **待决（事 B 前置）**：agent 的 `browser_act` / `browser_read` 作用于**哪个**浏览器实例。推荐「agent 固定绑定一个会话主视图，用户额外开的页签标记为『我的浏览』」——这样 agent 工具面零改动，⑦-A 仍成立
- **电平的状态别只用边沿的事件去同步**（B1 后续修复）：原生视图的矩形必须**一直**等于页面区域，而
  `ResizeObserver` / `window resize` 都是**边沿触发**——**漏一次边沿就永久错位**（实测抓到过 132px）。
  教训两条：电平状态要**周期性重申**兜底；**只验「会变」不验「相等」等于没验**。
  **同一个不变量要在不同「栏宽」下各验一次**（823 宽下验过，问题偏偏出在窄栏）
- **判「有没有溢出」别用会被 `overflow` 钳住的量**：`documentElement.scrollWidth` 在页面自带
  `overflow-x: hidden` 时**恒等于 `clientWidth`**（必然为真的假阴性）。要用 `body.scrollWidth` 或
  「遍历全元素取 `getBoundingClientRect().right` 的最大值」。
  另：「超出 / 显示不全」有**两种来源**——① 原生视图比页面区域大（覆盖）vs ② 页面自己比视口宽，
  **分开量**，别听描述就改代码
- **「在 DOM 里」不等于「用户点得到」**：小目标入口（徽标、按钮、页签）的断言要做**命中测试**
  （`document.elementFromPoint(中心)`），否则「字号看得见、按钮点不到」的假出口永远发现不了
- **信号对了但含义不对，比没有信号更糟**（C1 那次）：`faulted` 看着像「任务失败了」，其实是**会话级硬故障且不复位**。
  用内核字段前先读它的**定义与写入点**（`reducer.js` / `lane.js`），别按字段名猜语义
- **别把设计稿当能力清单**：原型的「+」菜单画了 终端 / 任务摘要 / 代码变更，产品里前两个**根本不存在**
  （代码变更是独立侧栏面板、不是页签）。做入口（菜单项 / 图标 / 按钮）前先问：**这东西现在真的存在吗？
  点下去有可见反馈吗？** 不存在的能力宁可不放（`AGENTS.md` §3.6）
- 通用纪律见 `AGENTS.md`（尤其 3.3 位移计算、3.5 设计前先读代码、3.6 别做死控件）
