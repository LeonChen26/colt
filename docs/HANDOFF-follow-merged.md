## 2. 定下的目标形态（这是本批的核心，不要重新讨论）

### 2.1 「正在处理」只由两段构成（规则 ⑦-G）

| 段 | 时态 | 内容 | 独有性 |
|---|---|---|---|
| **进行中的动作** | 此刻 | `runningTools` 逐条（工具名 + 参数摘要 + 相对时间） | 全应用唯一出处 |
| **本次改动（总账）** | 本次累计 | 一行：`N 处 · M 文件 +a −b`，点击进入清单 | 全应用唯一出处 |

硬约束（每条都有理由，别绕过）：

1. **进行中的动作只放「此刻在跑」的**。已完成的文件改动**不在这里重复列一遍**。
   理由：面板必须**能显示「空」**。若把已完成内容常驻在此，面板永远有内容，⑦-E 那句
   「它是活的吗」就再也答不出来——而这是自用场景判断安全性的第一依据。
2. **总账不是视图，不另立页签，也不固定在右栏底部**（用户已确认）。
   它属于「正在处理」这一视图：跟着该视图出现、随切页签消失。
   将来页签变多（浏览器 / 统计 / 规则 / 终端…）时，切走即不显示——那一刻用户在别的现场，
   「这次会话改了多少」不是他要看的东西。
3. **总账由「可折叠区段」降级为「一行状态」**：不是 `fsec`，没有 caret / 展开态 / 空态。
4. **数字只有一个口径**：`N 处 · M 文件`。
   「处」= 改动条数（`fileChanges.length`）；「文件」= 按路径去重后的文件数。
   此前两处都叫「N 文件」却给出两个不同的数（段二写 `byPath.size` 文件、改动面板写 `changes.length` 处），
   用户在同一屏看到「3 文件」与「7 处」无从理解，故**两个数都必须显式命名**。

### 2.2 「正在处理 → 清单 → diff → 文件内容」是一个东西的连续下钻（规则 ⑦-G）

- 原「改动」页签与「文件」页签**合并**为一个下钻路径，不再并列。
- 层级用**面包屑**表达（`正在处理 › 本次改动 › UI-REGIONS.md`），ESC 逐层回退。
- **清单层**（点总账进入）：
  - 按**目录分组**（吸收原「文件」视图右树的独有能力，但只是弱化的标签行，不额外消耗一次点击）
  - **同一文件多次编辑折叠为 `×N`**，点开才见 `#3 #2 #1` 历史
  - 行数 `+a −b` **只在这里出现一次**
  - ⚠️ **后续订正（v1.36）**：**总账也会显示 `±`**（不再只此一处）；且总账的「N 处 · M 文件」用的是**原始计数**（含项目外条目，`FollowPanel.tsx:97-102`），而清单头部用的是 `buildChangeList` 的**过滤后**计数（`ChangeDrilldown.tsx:367-368`）；`+a −b` 现在给的是**净值**（早期版本是逐次累加）。
- **diff 层**：该文件的 patch（同一文件多次编辑时给「历史 N / 最新」切换）
- **内容层**：文件本身（原「文件」视图的预览）
- **越界路径过滤**（`isProjectRelative`）必须扩到**所有可点入口**。
  原不一致：`buildFileTree` 过滤了（旧 `lib/file-tree.ts`），而 `FollowPanel` 段一的文件行**没有**——
  点进去是「无法预览该文件」的死条目。
  **✅ 已收口（v1.32）**：过滤统一在 `lib/change-list.ts` 的 `buildChangeList` 里做，
  清单是**唯一**的文件列表出口（段一的文件行已撤），清单底部如实写「已隐藏 N 个项目外文件」。
  ⚠️ 例外仍然保留：**④ 工具卡路径不过滤**——那是「模型确实碰过这个路径」，
  点进去要能看到主进程给的可读拒绝原因（A3-2 的越界断言正是靠它）。
- ⚠️ **已知能力缺口**（见 §6）：清单层吸收目录结构后，**整项目树**将无处安放，需另立页签，不要与清单混做。

### 2.3 附属视图给「结论」不给「流水」（规则 ⑦-H）

**核心判断**：`ToolsPanel` 列的是「工具名 + 耗时 + 成败 + 入参」，但**中栏会话流（④）的工具卡
是同一份数据且多一个「输出」**，还带「为什么调它」的对话上下文。所以面板不是「另一种看待方式」，
是**信息更少的副本**。

| 视图 | 聚合内容 |
|---|---|
| **统计**（原「用量」**改名**） | 总额（tokens / 费用）+ **按模型分组**（次数 / tokens / 费用 / 占比）+ **工具调用次数排行** + **工具耗时排行** + 失败统计 |
| **规则** | 不变（见 §2.4） |
| ~~工具~~ | **取消独立视图**：聚合**与明细**都并入「统计」 |

**「用量」改名为「统计」的理由**（2026-09 定）：
「用量」一词**在收窄自己**——它只盖得住费用与 tokens，「工具调用次数」「耗时排行」「失败率」
都不是「用量」。名实不副会让用户按名字建立错误预期。
「统计」涵盖「凡是从会话数据聚合出来的数」。

**两条硬约束**：

1. **排名必须带分母**（「共 42 次」），否则「排行」只是又一个列表。
2. **明细必须能被筛选，否则不算并入**：原 `ToolsPanel` 是无条件平铺全量流水，
   如果并入后仍是平铺，就只是换了个地方堆放。因此：
   **从聚合行点进去 → 明细自动筛成该维度**（点「耗时排行」的 `bash` → 明细只剩 bash 的 22 条），
   并至少提供「全部 / 只看失败」。这才让并入产生新能力——
   **④ 会话流给不了「只把 bash 挑出来看」**。
   - 明细**不归 ④**（用户 2026-09 定）：④ 的工具卡仍是**看单次调用**的最佳位置（有输出、有上下文），
     但「按维度筛全量」是聚合视图才有的能力，两者不重复。

**好消息**：聚合所需字段**全在现有协议里，不需要改 IPC**——
`ToolCallRecord` 已有 `toolName` / `durationMs` / `isError` / `createdAt`；
`UsageRecord` 已有 `model` / `inputTokens` / `outputTokens` / `cache*Tokens` / `costUsd`。

### 2.4 会话头按钮 4 个 → 2 个（规则 ⑦-H）
