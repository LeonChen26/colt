# 失败与错误处理

> **什么时候读这份**：写任何**可能失败**的路径之前——后台操作、工具调用、网络请求、模型调用。
>
> 这份文件的由来是一次真实事故：`/compact` 长期「点了没反应」，查到最后发现**失败发生了，但没人把它说出来**。
> 静默失败比报错更伤信任——报错至少让用户知道该换条路。

---

## 一、铁律：失败必须可见

**任何后台操作失败，用户都必须能看见。** 没有例外。

事故复盘（完整版在 `docs/UI-REGIONS.md` v1.38）：

- `/compact` 触发压缩 → 内核生成摘要失败 → 用户界面上**什么都没发生**，看起来像按钮坏了。
- 根因有**两层**，第二层才是真正让排查变难的那层：
  1. 请求被模型 400 掉（参数问题：`thinking: disabled` 遇上「始终思考」的模型，见 `docs/GLOSSARY.md` §七）；
  2. **失败路径不走 `Result.err`** —— 内核把摘要失败结算成 `ok: true` + `status: "failed"`，
     代码只检查了 `Result.err`，于是**静默**。

所以：**修掉 (1) 只是让这次不失败；修掉 (2) 才是让下次失败能被发现。**

---

## 二、内核错误的两条路径：两条都要查

**这是本文件最实用的一条。** 内核返回失败有**两种形态**，形制完全不同：

| 形态 | 出现在 | 何时发生 | 漏查的后果 |
|---|---|---|---|
| `Result.err` | 调用的返回值 | **accept 阶段**就被拒（参数、模型、权限） | 通常不会漏——错误直接抛出来 |
| `ok: true` + `status: "failed"` | 结算结果内部 | **接单了，但执行失败**（生成摘要时报错、网络断、密钥失效） | **静默**。因为「`ok` 是 true」，看着像成功 |

**结论**：判断「这件事成了没有」，**不能只看 `Result.err`**，必须**同时**检查结算状态。

参考实现：`src/worker/lib/compact-error.ts`（`describeCompactError` 处理 `Result.err`，
`describeCompactOutcome` 处理结算状态），单测在 `tests/compact-error.test.ts`。

## 三、陷阱：`ConversationView.faulted` **不能**当作「本轮失败」

`faulted` 这个名字非常自信，但它的语义不是「任务失败了」：

- 它**只在 harness 的 `fault` 事件上置位，且从不复位**——是**会话级硬故障**，不是轮次终态。
- 拿它做「已失败」信号会得到一个**永久灰条**：比没有信号更糟，因为它会**持续撒谎**。

**正确信号**是 `lastResult.status`：`completed` | `declined` | `aborted` | `failed`（附 `error`）。

> 这条是本仓 `AGENTS.md` 记过的「按字段名猜语义」事故。用外部依赖（内核、宿主、协议）的字段前，
> **先读它的定义与写入点**——尤其那种「名字很自信、却没人用过」的字段。`faulted` 在渲染层一处都没被读过，
> 这本身就是个信号。

## 四、怎么把错误翻成人话（映射约定）

宪法 #7：**显示真实原因 + 建议动作，不透传底层原始报错。**

翻一条错误，走三步：

| 步骤 | 做什么 | 例 |
|---|---|---|
| 1. **分类** | 按 `_tag` / `code` / `status` 归类，**不要**按错误字符串内容做 if-else | 「密钥没配」「网络不通」「被模型拒了」「上下文超限」 |
| 2. **一句话原因** | 说清**发生了什么**，用用户能懂的词 | 「模型服务拒绝了这次请求」而不是 `EAI_AGAIN` |
| 3. **建议动作** | 给一条**可执行**的下一步 | 「去设置里检查密钥」「稍后重试」「先压缩上下文」 |

### 呈现位置

| 场景 | 呈现在哪 |
|---|---|
| 后台操作失败但会话还能继续（压缩、分析器） | 会话流的**提示条**（例：压缩失败是红色横条，成功是绿色并带「压缩前约 N tokens」） |
| 轮次结束的异常态 | Live Bar 的**运行态**：`运行中` / `已中断` / `已失败` / `空闲`（`lib/format.ts` 的 `runStateOf`） |
| 需要用户决策的阻塞 | **授权卡**（四档决定 + 可见倒计时 + 超时转「已超时自动拒绝」） |
| 会话进程本身出错 | `session.error` 事件 |

⚠️ **失败文案也要覆盖「没失败但什么也没发生」**：如果操作合法地什么都没做（比如没有可压缩的内容），
也要给一句话——「没反应」与「静默失败」在用户眼里**长得一样**。

**反例（v1.39，第二个真实事故）**：输入区拖入非图片文件时，`addFiles` 直接 `return`——
附件通道只承载图片（内核 `imageInput` 语义）**不是缺陷，没说出来才是**。
这里还多一层：「说出来」不等于「画在某个提示条上」，得落在**用户动手的那个位置**。
最顺手的选择是现成的顶部那条 `error`，但它挂在消息流顶部、跟着消息一起滚——
消息滚到底时用户根本看不到，**等于没说**。最终改成贴在输入卡片内（`data-conv-attach-notice`），
并点名被跳过的文件名。判据也据此写成「提示在**卡片内**」，而不是「页面上存在这行字」。

## 五、写测试时的断言纪律

1. **不要断言内核给出的错误字符串。** 只认 `net::ERR_` 前缀。
   例：`http://127.0.0.1:9/refused` 实测报的是 **`net::ERR_UNSAFE_PORT`**（9 在 Chromium 受限端口名单里），
   不是想当然的 `ERR_CONNECTION_REFUSED`——写死字符串必然误红。
2. **写剪贴板的断言前先 `window.focus()`。** `navigator.clipboard.writeText` 在文档未聚焦时**直接 reject**，
   冒烟跑的时候焦点还在终端上 → **静默失败**。真实用户点按钮时窗口必然聚焦，所以这不是产品缺陷，
   是**测试环境**缺了前提。
3. **用例红了先怀疑用例的判据，再怀疑产品。** 净值那条断言首跑变红，是因为用例拿**整行文字**去比 `−1`；
   产品没问题。同类还有「选择器太松」——别用 `button[aria-pressed]` 当页签选择器（容器里还有别的可切换控件）。
4. **只验「会变」不验「相等」等于没验。** 断言要按不变量写（例如原生视图矩形与页面区域**逐像素相等**），
   而不是「收起时会变高」。

## 六、新增一个可能失败的操作：五问清单

写代码前问自己五件事，缺一件就别提交：

1. **失败会不会被看见？** 用户能不能从界面上知道「它失败了」，而不是「它没反应」？
2. **两条路径都查了吗？** `Result.err` **和**结算状态（`ok:true` + `status:"failed"`）都处理了？
3. **文案有没有「原因 + 建议动作」？** 有没有把底层原始报错直接透传给用户？
4. **有没有误用会撒谎的字段？** 用的是 `lastResult.status`，还是那个从不复位的 `faulted`？
5. **提示落在用户动手的那个位置了吗？** 合法的「什么都没做」（拖入非图片、无可压缩内容）
   同样要说出原因，而且**说在他手边**——挂在滚动区的顶部、或要切页签才看得到的提示，等于没说。
